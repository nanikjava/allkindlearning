Partitions, shards and replicas

These three words all describe "splitting up" or "copying" a table, so they get mixed up. They work at different levels and solve different problems. This page explains each one in depth, shows how they stack on top of each other in the tutorial's prod cluster (2 shards × 2 replicas + 3 Keepers), and points to the lesson SQL where you can watch each one happen.

Partition

How is data split inside one table on one server?

By a key such as month. Each partition is a group of folders on disk. Used for data lifecycle: drop, detach, move, TTL.

Shard

Which server holds this row?

Rows are spread across servers by a sharding key. Each shard holds a different slice. Used to scale beyond one machine.

Replica

How many copies of this slice exist?

Each shard is copied to other servers. Every replica holds the same rows. Used for availability and read capacity.

1. The big picture

Read the diagram from the outside in. The cluster is split into shards. Each shard is stored on two servers that are replicas of each other. Inside every server, the table's data is split into partitions by month. The three Keeper nodes coordinate replication; they hold metadata, never table data.

Put another way, each concept is a different axis:

  • Partitioning slices within a table on one node, usually by time.
  • Sharding slices across nodes, usually by an entity like tenant or user.
  • Replication doesn't slice anything. It makes copies of each shard.

Total servers = shards × replicas. Total distinct data = the sum of all shards. Every server holds roughly 1 / shards of the data, and inside that, it is split into partitions.

3. Partitions in depth

What a partition is

Every MergeTree table stores its rows in parts: immutable folders, one per insert, which background merges combine into bigger parts. A partition is a rule that says which parts may be merged together. Two parts merge only if they belong to the same partition. So with PARTITION BY toYYYYMM(event_time), June rows and July rows never end up in the same folder.

CREATE TABLE shop.ev_lifecycle AS shop.events
ENGINE = MergeTree
PARTITION BY toYYYYMM(event_time)      -- one partition per month
ORDER BY (tenant_id, event_time)       -- sort order inside every part
SETTINGS ttl_only_drop_parts = 1;

On disk, a part folder is named after its partition: 202606_1_8_2 means partition 202606, block numbers 1 to 8, merge level 2 (it went through two rounds of merges). A part changed by a mutation gets a fifth number, the mutation version, as in 202606_1_8_2_11.

What partitions are good for

  • Cheap deletes of old data. ALTER TABLE ... DROP PARTITION 202501 marks the partition's parts inactive at once, and the files are deleted in the background about 10 minutes later. No rows are rewritten. Compare with ALTER TABLE ... DELETE WHERE, which rewrites every affected part.
  • TTL that lines up. With ttl_only_drop_parts = 1, an expired TTL drops whole parts instead of rewriting them. That works well when parts never mix old and new rows, which monthly partitions guarantee.
  • Detach and attach. Lesson 02 detaches 202606; the count drops instantly and comes back on attach. Useful to quarantine bad data or move it between tables.
  • Tiered storage. Move old partitions to a cheaper disk or S3 with MOVE PARTITION ... TO DISK or a TTL ... TO VOLUME rule.
  • Re-loading one slice. Load a corrected month into a staging table, then REPLACE PARTITION 202606 FROM staging swaps it atomically.
  • Some query pruning. Each part keeps min/max values of the partition key columns. A query filtering on event_time skips partitions that can't match.

What partitions are not for

Partitioning is not the main tool for query speed. The primary key (ORDER BY) and its sparse index already skip granules inside every part, and they work at a much finer grain than months. Lesson 02's 01_order_by.sql shows the effect of ORDER BY; partitioning by tenant to "make tenant queries faster" would do nothing ORDER BY (tenant_id, ...) doesn't already do, while multiplying the number of parts.

Pitfalls

  • Too many partitions. Every insert creates at least one part per partition it touches. Partition by day with years of history, or by a high-cardinality column like user_id, and you get thousands of tiny parts, slow merges and the error Too many partitions for single INSERT block (limit max_partitions_per_insert_block, default 100). The docs' guidance: most tables don't need a partition key at all, most of the rest don't need anything finer than a month (by day is common for observability data), and more than about a thousand partitions is too many. Never partition by a client id or name.
  • Inserts spanning many months. Backfills that send years of data in one block produce one part per month. Group backfills by month.
  • Expecting partitions to spread load. All partitions of a table live on the same server. Spreading across servers is sharding.

4. Sharding in depth

What a shard is

A shard is a server (or a group of replica servers) that holds one slice of the table's rows. Each shard has its own ordinary local table, here shop.events_local. Nothing inside a local table knows it is part of something bigger. The sharding happens in a separate Distributed table, which stores no data of its own. It is a router that knows the cluster layout and the sharding key.

-- Distributed(cluster, database, local_table, sharding_key)
CREATE TABLE shop.events_all ON CLUSTER prod AS shop.events_local
ENGINE = Distributed(prod, shop, events_local, cityHash64(tenant_id));

The cluster layout comes from remote_servers in cluster.xml: two <shard> blocks, each listing two <replica> hosts.

The sharding algorithm: weighted modulo

ClickHouse does not use consistent hashing, a hash ring or a directory of key ranges. The Distributed engine uses a plain weighted modulo, described in the Distributed engine docs:

  1. Evaluate the sharding key expression for the row. It must return an integer. It can be any expression of constants and columns, so the hash function is your choice: cityHash64(tenant_id), intHash64(user_id), rand(), or even a raw integer column.
  2. Divide by the sum of all shard weights and take the remainder.
  3. Each shard owns a half-open range of remainders, in the order shards appear in remote_servers: shard i gets [sum of earlier weights, sum of earlier weights + its weight). The row goes to the shard whose range contains the remainder.

Each <shard> can set a <weight>; the default is 1. In this tutorial both shards have weight 1, so the total is 2: remainder 0 goes to shard 01 and remainder 1 to shard 02. That is just cityHash64(tenant_id) % 2.

What weighted modulo means in practice

  • The key must spread well. Modulo of a raw column inherits its patterns (tenant ids that are all even would all land on shard 01), which is why the key is wrapped in a hash such as cityHash64.
  • Weights handle uneven hardware. Give a bigger server a bigger weight and it receives a proportionally bigger share of new rows.
  • No automatic rebalancing. Changing the shard list or a weight changes the divisor, so most keys now map to a different shard. The rows already written stay where they are. Nothing moves data for you. The docs suggest adding a new shard with a heavier weight so it fills up faster, accepting a somewhat uneven layout.
  • Old and new rows for one key can split. After a change, tenant 42's earlier rows may sit on shard 01 while its new rows go to shard 03. Queries through events_all still return correct results because they ask every shard, but optimize_skip_unused_shards computes the shard from the current layout and would skip the shard holding the old rows. Don't use shard pruning across a layout change until the data has been rewritten.
  • The rule only applies to writes through the Distributed table. An ingester that inserts straight into events_local must apply the same formula itself, or shard pruning and per-shard dedup stop being reliable.

The write path

  • You can insert into events_all on any node. It computes the shard for each row and forwards rows.
  • By default the forwarding is asynchronous: rows are written to a local queue folder and sent in the background. The INSERT returns before the shards have the data. Set distributed_foreground_insert = 1 to wait, or check system.distribution_queue for a backlog.
  • Many production setups skip the router for writes: the ingester computes the shard itself and inserts directly into events_local on a node of that shard. Fewer hops, bigger blocks, no hidden queue.
  • Because <internal_replication>true</internal_replication> is set, the router sends each row to one replica of the shard and lets ReplicatedMergeTree copy it. false is actually the default. With it, the router writes to every replica itself, and the docs warn that replica consistency is then never checked, so over time replicas drift apart. Always use true with replicated tables.

The read path

  • The initiating node sends the query to one replica of every shard (chosen by load_balancing). Each runs it on its local table and returns partial aggregates. The initiator merges them.
  • Aggregations parallelise almost perfectly. ORDER BY ... LIMIT needs each shard to send its top N.
  • Shard pruning. Lesson 06 queries WHERE tenant_id = 42 with optimize_skip_unused_shards = 1, then reads query_log on all hosts to show only one shard ran a sub-query.
  • JOINs and IN across shards. A plain JOIN against another Distributed table runs a sub-query from every shard to every shard. Use GLOBAL JOIN/GLOBAL IN to ship the small side once, or shard both tables on the same key so the join is local.

Choosing the sharding key

KeyGoodBad
cityHash64(tenant_id)All of a tenant on one shard: per-tenant queries hit one shard, tenant-level joins stay localOne huge tenant makes a hot shard
cityHash64(tenant_id, user_id)Spreads big tenants evenly; per-user data stays togetherPer-tenant queries touch every shard

toYYYYMM(event_time)Nothing usefulAll current writes land on one shard. Time belongs in the partition key, not the sharding key

Pitfalls

  • Resharding is manual. Adding a third shard to remote_servers only affects new rows (see weighted modulo above). Existing rows stay where they are and the cluster stays unbalanced until you copy data into a new layout (for example, INSERT INTO new_all SELECT * FROM old_all, partition by partition).
  • Shard too early. One ClickHouse server handles billions of rows. Shard when one machine can't hold the data or keep up with inserts or query CPU, not before.
  • Uniqueness is per shard. ReplacingMergeTree and dedup only work within a shard, so rows that must collapse together must share a sharding key.

5. Replication in depth

What a replica is

A replica is another server holding the same data as its shard-mates. In ClickHouse, replication is per table: a table is replicated because its engine is ReplicatedMergeTree. Two tables are replicas of each other when they register at the same Keeper path with different replica names.

ENGINE = ReplicatedMergeTree('/clickhouse/tables/{shard}/shop/events_local', '{replica}')
--                             ^ same on both replicas of a shard     ^ unique per node

The {shard} and {replica} macros come from <macros> in cluster.xml, filled from the SHARD and REPLICA environment variables in docker-compose.yml. So ch-s1r1 and ch-s1r2 both use /clickhouse/tables/01/… and become replicas; ch-s2r1 uses /02/… and is a separate shard. One DDL statement run ON CLUSTER creates the right thing on all four nodes. This is the link between sharding and replication: the Keeper path decides who is a replica of whom.

How it works

  1. An INSERT reaches any replica. That replica writes a new part locally, as a plain MergeTree would.
  2. It records the part in Keeper: a log entry saying "part X exists" plus a hash of the inserted block.
  3. Every other replica watches the log, copies the entry into its own queue and downloads the part from a replica that has it.
  4. Merges are scheduled the same way: one replica decides "merge parts A+B into C" and writes it to the log; the others either perform the same merge or fetch the result.
  5. There is no leader for writes. Any replica can accept inserts (multi-master).

Consistency knobs (Lesson 05, 03_consistency.sql)

  • Default is asynchronous. The INSERT returns when one replica has the part. If that node dies before the others fetch it, the insert can be lost.
  • insert_quorum = 2 (or 'auto' for a majority) waits until N replicas have the part. Slower, safer.
  • Read-your-writes. Another replica may not have your rows yet. Pin a client to one replica, run SYSTEM SYNC REPLICA, or use select_sequential_consistency = 1. That last option only works with quorum inserts and insert_quorum_parallel = 0 (the default is 1).
  • Deduplication. The block hash in /blocks means the same block inserted twice is stored once. The lesson inserts the same purchase twice and counts 1 row. This is what makes ingester retries safe. It is on by default (insert_deduplicate = 1) and Keeper remembers the last 10,000 block hashes per table (replicated_deduplication_window).

What happens when things fail

Lesson 09's failure drills (drill.sh) stop replicas and Keeper nodes so you can watch each row of this table happen.

Pitfalls

  • Replication is not a backup. A bad ALTER ... DELETE, DROP PARTITION or TRUNCATE is replicated to every replica within moments. DROP TABLE on its own runs only on the server you send it to (the docs list CREATE, DROP, ATTACH, DETACH and RENAME as not replicated), but with ON CLUSTER it runs everywhere. Lesson 07 covers backups.
  • Replicas don't add write capacity. Every replica stores and merges every part. Two replicas double the disk and the merge CPU for the same data.
  • Keeper is critical. Run 3 (or 5) Keeper nodes on separate hosts with fast disks. Watch is_readonly and absolute_delay in system.replicas.
  • Copy-paste Keeper paths. Two different tables with the same path become each other's replicas and mix data. Include database and table name in the path (or use {uuid}).

7. Common confusions

"Partitions spread data across servers."
No. Partitions are folders on one server. In other databases (PostgreSQL declarative partitioning, Hive, BigQuery) the word also means a local split, but in Kafka "partition" means something closer to a shard. In ClickHouse, cross-server splitting is always called sharding.
"More partitions make queries faster."
Usually the opposite. More partitions means more, smaller parts and more files to open. Speed comes from ORDER BY, skip indexes and projections.
"Replicas split the work of one query."
By default one query uses one replica per shard. Replicas raise how many queries you can run at once. (The parallel replicas feature can split one query across the replicas of a shard. It is a beta feature you turn on with enable_parallel_replicas, and max_parallel_replicas caps how many replicas take part.)
"A shard is a server."
A shard is a slice of data. In this cluster each shard lives on two servers. Without replication a shard happens to be one server.
"The Distributed table stores the data."
It stores nothing except an outgoing insert queue. Drop it and no data is lost; drop events_local and that server's copy of the data is gone. With ON CLUSTER, as the lessons run it, every copy is gone.
"Replication makes backups unnecessary."
Replication copies mistakes as faithfully as data. See Lesson 07.

8. Choosing what you need

These are independent decisions. Most tables want a partition key; many deployments want replication; fewer need sharding.

SituationPartitionShardReplicate
Dev laptop, Lesson 01 single nodeBy month if you'll expire dataNoNo
Production, data fits one server comfortablyBy monthNo (1 shard)Yes, 2 replicas + 3 Keepers
Data or ingest outgrows one serverBy monthYes, by an entity keyYes, 2 per shard
Read-heavy dashboards, data fits one serverBy monthNoYes, more replicas for concurrency
Small lookup / dimension tableNone (tuple() or omit)No; replicate to every node so joins stay localYes

Rough order of decisions: pick ORDER BY first (query speed), then PARTITION BY (retention granularity), then replication (availability), and shard last, only when one replica set runs out of room.

Queries that show all three at once on the cluster:

-- Rows per host: replicas of a shard match, shards differ
SELECT hostName() AS host, getMacro('shard') AS shard, count() AS rows
FROM clusterAllReplicas('prod', shop.events_local)
GROUP BY host, shard ORDER BY host;

-- Partitions and parts on every host
SELECT hostName() AS host, partition, count() AS parts, sum(rows) AS rows
FROM clusterAllReplicas('prod', system.parts)
WHERE database = 'shop' AND table = 'events_local' AND active
GROUP BY host, partition ORDER BY host, partition;

-- Replication health
SELECT hostName() AS host, replica_path, is_readonly, absolute_delay, queue_size, active_replicas
FROM clusterAllReplicas('prod', system.replicas)
WHERE table = 'events_local';
