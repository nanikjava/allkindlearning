Best practices for building applications on ClickHouse

Most ClickHouse advice is written from the server's point of view: engines, merges, codecs. This page is written from the application's point of view. Each section is one practice your service code should follow, why it matters, and a Go example using clickhouse-go/v2 (the same driver as the tutorial's go-client/). Examples use the tutorial's shop.events table.

ClickHouse is a freight train, not a taxi. It moves enormous loads very fast, but it hates being asked to stop for one passenger at a time. Almost every practice below is a way of loading the train in big, planned batches and asking it questions it was built to answer.

1. Reference architecture

Split your application into a write path and a read path, each with its own service, ClickHouse user and limits. Raw events land in one table; materialized views keep small rollup tables up to date; the API reads rollups first.

ComponentResponsibilityOwns which practices
NATS JetStream + ingest serviceHold events durably, then turn them into large, idempotent inserts4, 5, 6, 7
API serviceAnswer bounded, tenant-scoped questions quickly9, 11, 13, 14
Schema (MVs, rollups)Pre-compute what the API asks most often2, 8, 10
PlatformUsers, limits, migrations, monitoring12, 15, 17

2. Design the schema from your app's queries

The rule

Write down the 5 to 10 queries your app will run most, then pick ORDER BY so the columns every one of them filters on come first.

The sorting key is the only "index" ClickHouse uses to skip data. If every API call filters by tenant and a time range, ORDER BY (tenant_id, event_time) lets ClickHouse read a few granules instead of the whole table. Lesson 02 measures this: the same query reads orders of magnitude fewer rows with the right key.

The sorting key is the order of books on a library shelf. If the shelf is sorted by author and every visitor asks for an author, they walk straight to it. If visitors ask for a publication year, they read every spine.
CREATE TABLE shop.events
(
    event_time  DateTime64(3, 'UTC'),
    tenant_id   UInt32,
    user_id     UInt64,
    event_type  LowCardinality(String),
    country     LowCardinality(String),
    url         String,
    duration_ms UInt32
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(event_time)          -- lifecycle (TTL, drop), not speed
ORDER BY (tenant_id, event_type, event_time) -- what the app filters on, coarse to fine
TTL toDateTime(event_time) + INTERVAL 13 MONTH;

Do this now: grep your codebase (or system.query_log) for the WHERE clauses you actually send, and check that their leading columns match the table's sorting key.

3. One connection pool per process

The rule

Create the driver.Conn once at startup, share it everywhere, list every replica, and set dial and read timeouts.

clickhouse.Open returns a pool, not a single connection. Opening one per request wastes TCP and TLS handshakes and can exhaust max_connections on the server. Listing all replicas lets the driver fail over when one node is down.

// One pool per process. Pass it to repositories; never open per request.
func NewClickHouse(ctx context.Context, cfg Config) (driver.Conn, error) {
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr:             cfg.Addrs, // every replica, e.g. ch-1a:9440, ch-1b:9440, ch-2a:9440, ch-2b:9440
		Auth:             clickhouse.Auth{Database: "shop", Username: cfg.User, Password: cfg.Password},
		TLS:              &tls.Config{MinVersion: tls.VersionTLS12},
		ConnOpenStrategy: clickhouse.ConnOpenRoundRobin, // spread load, skip dead nodes
		DialTimeout:      5 * time.Second,
		ReadTimeout:      30 * time.Second,
		MaxOpenConns:     20,
		MaxIdleConns:     10,
		ConnMaxLifetime:  10 * time.Minute, // rebalance after a node comes back
		Compression:      &clickhouse.Compression{Method: clickhouse.CompressionLZ4},
		ClientInfo: clickhouse.ClientInfo{
			Products: []struct{ Name, Version string }{{Name: "orders-api", Version: cfg.Version}},
		},
	})
	if err != nil {
		return nil, err
	}
	pingCtx, cancel := context.WithTimeout(ctx, 5*time.Second)
	defer cancel()
	if err := conn.Ping(pingCtx); err != nil {
		return nil, fmt.Errorf("clickhouse ping: %w", err)
	}
	return conn, nil
}
ProtocolPick it whenTrade-off
Native (9000 / 9440)Go services you control; bulk insertsFastest, columnar blocks; needs a TCP load balancer if you use one
HTTP (8123 / 8443)Behind HTTP proxies, chproxy, serverlessEasier to route and inspect; somewhat more overhead per row

Size MaxOpenConns to your real concurrency. Each running query holds a connection for its whole duration, so a pool of 20 means at most 20 concurrent ClickHouse queries from this process.

4. Batch writes in the application

The rule

Never insert one row per event. Buffer and flush every 10k to 100k rows or every 1 to 5 seconds, whichever comes first.

Every INSERT creates at least one immutable part on disk. Background merges combine parts. If you create parts faster than merges can combine them, ClickHouse first slows inserts down and then rejects them with TOO_MANY_PARTS (code 252).

Think of a dishwasher. Running it once per spoon is wasteful and the kitchen floods with half-clean cutlery. Fill it, then run it.

In this architecture producers publish events to NATS JetStream (setup in section 6), and the ingest service pulls them in large batches. Fetch returns when it has maxRows messages or maxWait has passed, which is exactly the "N rows or T seconds" rule. Messages are acknowledged only after ClickHouse accepts the insert, so nothing is lost if the pod or ClickHouse dies mid-batch.

// Ingester pulls events from JetStream and writes them to ClickHouse in large batches.
type Ingester struct {
	conn    driver.Conn
	cons    jetstream.Consumer // durable pull consumer, shared by all ingest pods
	maxRows int                // e.g. 50_000
	maxWait time.Duration      // e.g. 1 * time.Second
}

func (in *Ingester) Run(ctx context.Context) {
	for ctx.Err() == nil {
		batch, err := in.cons.Fetch(in.maxRows, jetstream.FetchMaxWait(in.maxWait))
		if err != nil {
			log.Printf("fetch: %v", err)
			time.Sleep(time.Second)
			continue
		}
		msgs := make([]jetstream.Msg, 0, in.maxRows)
		rows := make([]Event, 0, in.maxRows)
		for m := range batch.Messages() {
			var e Event
			if err := json.Unmarshal(m.Data(), &e); err != nil {
				_ = m.Term() // poison message: never redeliver
				continue
			}
			msgs, rows = append(msgs, m), append(rows, e)
		}
		if len(rows) > 0 {
			// Detach from ctx so a shutdown signal does not abort a half-sent batch.
			in.handle(context.WithoutCancel(ctx), msgs, rows)
		}
	}
}

func (in *Ingester) handle(ctx context.Context, msgs []jetstream.Msg, rows []Event) {
	token := batchToken(msgs) // stable ID for this batch (section 6)
	err := in.sendWithRetry(ctx, token, rows)
	if err != nil && !retryable(err) {
		log.Printf("batch of %d rows rejected, sending to dead-letter: %v", len(rows), err)
		deadLetter(rows)
	}
	for _, m := range msgs {
		switch {
		case err == nil:
			_ = m.Ack()
		case retryable(err): // ClickHouse down or overloaded: events stay in the stream
			_ = m.NakWithDelay(10 * time.Second)
		default: // bad data or schema bug: retrying will never work
			_ = m.Term()
		}
	}
}

func (in *Ingester) send(ctx context.Context, rows []Event) error {
	batch, err := in.conn.PrepareBatch(ctx,
		"INSERT INTO shop.events (event_time, tenant_id, user_id, event_type, country, url, duration_ms)")
	if err != nil {
		return err
	}
	for _, e := range rows {
		if err := batch.Append(e.EventTime, e.TenantID, e.UserID, e.EventType, e.Country, e.URL, e.DurationMs); err != nil {
			_ = batch.Abort()
			return err
		}
	}
	return batch.Send()
}
Do
  • Sort the batch by the table's partition key if it spans many months, so one insert touches few partitions
  • Set the consumer's MaxAckPending above maxRows, or Fetch can never fill a batch
  • Export batch size, insert latency and consumer lag (pending messages) as metrics
Don't
  • Insert from an HTTP handler, one row per request
  • Ack messages before the insert succeeds; that turns a crash into data loss
  • Insert into many partitions in one batch (limit: max_partitions_per_insert_block, default 100)

5. Use async inserts when you cannot batch

The rule

If many independent writers each send a few rows (serverless functions, edge agents, many pods), let the server batch for you with async_insert=1.

With async inserts, ClickHouse collects small inserts in memory and writes them as one part when the buffer reaches a size or age threshold. Keep wait_for_async_insert=1 so your code only gets success after the data is actually written.

func InsertFew(ctx context.Context, conn driver.Conn, e Event) error {
	ctx = clickhouse.Context(ctx, clickhouse.WithSettings(clickhouse.Settings{
		"async_insert":          1,
		"wait_for_async_insert": 1, // ack only after the server flushed to a part
	}))
	return conn.Exec(ctx,
		`INSERT INTO shop.events (event_time, tenant_id, user_id, event_type, country, url, duration_ms)
		 VALUES (?, ?, ?, ?, ?, ?, ?)`,
		e.EventTime, e.TenantID, e.UserID, e.EventType, e.Country, e.URL, e.DurationMs)
}
StrategyBest whenWatch out for
NATS JetStream + batch consumer (sections 4 and 6)You control the producers and must not lose events during spikes or ClickHouse outagesOne more (small) system to run; delivery is at-least-once
Async insert, wait=1Many small writers you cannot coordinateEach call waits up to the flush timeout (about 200 ms by default) before it returns
Async insert, wait=0Fire-and-forget telemetry where loss is acceptableErrors are invisible to the app; a server crash loses the in-memory buffer

6. Make retries idempotent

The rule

When an insert fails, retry the same batch with the same rows in the same order and the same insert_deduplication_token.

A timeout does not tell you whether the server wrote the data. If you retry with a different batch you might write it twice. ClickHouse deduplicates a repeated insert block on replicated tables: if the token (or block hash) matches a recent insert, the retry is a no-op.

// withToken tags the insert so ClickHouse drops it if the same batch was already written.
// batchToken derives the token from the JetStream sequence range, so a redelivery of the
// exact same messages produces the same token and is dropped by ClickHouse.
func batchToken(msgs []jetstream.Msg) string {
	first, _ := msgs[0].Metadata()
	last, _ := msgs[len(msgs)-1].Metadata()
	return fmt.Sprintf("events-%d-%d", first.Sequence.Stream, last.Sequence.Stream)
}

func withToken(ctx context.Context, token string) context.Context {
	return clickhouse.Context(ctx, clickhouse.WithSettings(clickhouse.Settings{
		"insert_deduplication_token": token,
	}))
}

func (in *Ingester) sendWithRetry(ctx context.Context, token string, rows []Event) error {
	ctx = withToken(ctx, token) // same token on every attempt

	backoff := 200 * time.Millisecond
	for attempt := 1; ; attempt++ {
		err := in.send(ctx, rows)
		if err == nil || !retryable(err) || attempt == 6 {
			return err
		}
		jitter := time.Duration(rand.Int64N(int64(backoff / 2)))
		time.Sleep(backoff + jitter)
		backoff = min(backoff*2, 10*time.Second)
	}
}

Deduplication happens in the Replicated*MergeTree tables and keeps the last 100 blocks by default (replicated_deduplication_window). Plain MergeTree needs non_replicated_deduplication_window set above 0. Through a Distributed table, prefer synchronous distributed inserts (distributed_foreground_insert=1) so the retry reaches the same dedup check. In-process retries reuse the exact batch, so they are always deduplicated. After a Nak, JetStream may redeliver the messages in a different grouping, which gives a new token; if the first insert had actually landed, that can create duplicates. Treat the pipeline as at-least-once and use ReplacingMergeTree (section 8) on tables where a rare duplicate matters.

Absorb spikes and outages with NATS JetStream

Retries cover blips of a few seconds. For a longer outage (a ClickHouse upgrade, a Keeper problem) or a traffic spike, events need somewhere durable to wait. NATS JetStream is a good fit for this: a single Go binary, a 3-node cluster for high availability, persistent streams with acknowledgements and replay, and a first-class Go client. It gives you the decoupling of a message broker without the operational weight of a large broker cluster.

A post office sorting bin. Letters (events) wait in the bin until a courier (an ingest pod) takes a bundle and signs for it after delivery. If the courier never signs, the bundle goes back in the bin for the next courier. Several couriers can work from the same bin.
// One-time setup (or run it at ingest startup; CreateOrUpdate is idempotent).
func setupStream(ctx context.Context, js jetstream.JetStream) (jetstream.Consumer, error) {
	_, err := js.CreateOrUpdateStream(ctx, jetstream.StreamConfig{
		Name:       "EVENTS",
		Subjects:   []string{"events.>"},       // events.<tenant>.<type>
		Storage:    jetstream.FileStorage,
		Replicas:   3,                            // survives one NATS node down
		MaxAge:     72 * time.Hour,               // how long ClickHouse can be down without loss
		MaxBytes:   50 << 30,                      // 50 GiB cap
		Discard:    jetstream.DiscardNew,         // when full, reject publishes: backpressure to producers
		Duplicates: 2 * time.Minute,              // window for publish dedup by message ID
	})
	if err != nil {
		return nil, err
	}
	return js.CreateOrUpdateConsumer(ctx, "EVENTS", jetstream.ConsumerConfig{
		Durable:       "clickhouse-ingest",       // all ingest pods share it and split the work
		AckPolicy:     jetstream.AckExplicitPolicy,
		AckWait:       2 * time.Minute,           // longer than insert + all in-process retries
		MaxAckPending: 200_000,                   // must exceed batch size x number of pods
		MaxDeliver:    20,                        // then the message is dropped; alert on it
	})
}

// Producer side: publish with a message ID so a producer retry is not stored twice.
func Publish(ctx context.Context, js jetstream.JetStream, e Event, eventID string) error {
	data, err := json.Marshal(e)
	if err != nil {
		return err
	}
	subject := fmt.Sprintf("events.%d.%s", e.TenantID, e.EventType)
	_, err = js.Publish(ctx, subject, data, jetstream.WithMsgID(eventID))
	return err // an error here (for example stream full) is the producer's signal to slow down
}

7. Classify errors and apply backpressure

The rule

Retry only errors that can succeed later; fail fast on the rest; slow down producers when ClickHouse says it is overloaded.

// retryable reports whether trying the same request again may succeed.
func retryable(err error) bool {
	if errors.Is(err, context.Canceled) || errors.Is(err, context.DeadlineExceeded) {
		return false // the caller gave up; do not keep going
	}
	var ex *clickhouse.Exception
	if errors.As(err, &ex) {
		switch ex.Code {
		case 159, // TIMEOUT_EXCEEDED
			202, // TOO_MANY_SIMULTANEOUS_QUERIES
			209, // SOCKET_TIMEOUT
			210, // NETWORK_ERROR
			241, // MEMORY_LIMIT_EXCEEDED (server busy, may pass later)
			242, // TABLE_IS_READ_ONLY (replica lost Keeper)
			252, // TOO_MANY_PARTS (back off longer)
			319, // UNKNOWN_STATUS_OF_INSERT (retry with the same token)
			999: // KEEPER_EXCEPTION
			return true
		}
		return false // 62 syntax, 60 unknown table, 53 type mismatch, 497 access denied, 516 auth...
	}
	var ne net.Error
	return errors.As(err, &ne) || errors.Is(err, io.EOF) || errors.Is(err, syscall.ECONNRESET)
}
SignalApp response
252 TOO_MANY_PARTSPause flushing for seconds, grow the batch size, alert. It means you insert too often.
202 / 241 on readsReturn 503 with Retry-After; do not hammer the server with instant retries
242 read-only replicaRetry; the driver's round-robin will try another replica. Page someone if it persists (Keeper problem).
Syntax, type, auth errorsNever retry. Send the batch to a dead-letter store and alert; it is a deploy bug.

8. Model changes as appends, not updates

The rule

ClickHouse is not your OLTP database. Write a new version of a row instead of updating it, and let the engine collapse versions.

ALTER TABLE ... UPDATE is a mutation: it rewrites whole parts in the background. Fine for a rare fix, terrible as an app code path. For entities that change (order status, user profile), insert each change with a version and use ReplacingMergeTree.

A ledger, not a whiteboard. You never erase a line; you add a new line and the latest one wins.
CREATE TABLE shop.orders
(
    order_id   UInt64,
    tenant_id  UInt32,
    status     LowCardinality(String),
    amount     Decimal(12,2),
    updated_at DateTime64(3, 'UTC'),
    is_deleted UInt8 DEFAULT 0
)
ENGINE = ReplacingMergeTree(updated_at, is_deleted)
ORDER BY (tenant_id, order_id);
// "Update" = insert the new state. Merges eventually keep only the latest version.
func (r *OrderRepo) SetStatus(ctx context.Context, o Order, status string) error {
	return r.conn.Exec(ctx,
		`INSERT INTO shop.orders (order_id, tenant_id, status, amount, updated_at) VALUES (?, ?, ?, ?, ?)`,
		o.ID, o.TenantID, status, o.Amount, time.Now().UTC())
}

// Reads must tolerate unmerged duplicates: use FINAL (simple) or argMax (often faster on big scans).
const currentOrders = `
SELECT order_id, argMax(status, updated_at) AS status
FROM shop.orders
WHERE tenant_id = {tenant:UInt32}
GROUP BY order_id`

Keep personal data out of ClickHouse where you can (store a surrogate ID and keep the identity in your OLTP store). Deletes in a columnar store are always more expensive than in a row store.

9. Bound every read: params, timeouts, limits

The rule

Every query from the app uses bound parameters, a context deadline, a server-side max_execution_time, a result cap, and a tag.

type PageStat struct {
	URL   string
	Views uint64
}

func (r *Repo) TopPages(ctx context.Context, tenant uint32, from, to time.Time, limit int) ([]PageStat, error) {
	ctx, cancel := context.WithTimeout(ctx, 3*time.Second)
	defer cancel()

	queryID := uuid.NewString()
	log.Printf("request=%s clickhouse_query_id=%s", requestID(ctx), queryID) // link app logs to query_log

	ctx = clickhouse.Context(ctx,
		clickhouse.WithQueryID(queryID),
		clickhouse.WithParameters(clickhouse.Parameters{ // server-side binding: no SQL injection
			"tenant": strconv.FormatUint(uint64(tenant), 10),
			"from":   from.UTC().Format(time.DateTime),
			"to":     to.UTC().Format(time.DateTime),
			"lim":    strconv.Itoa(limit),
		}),
		clickhouse.WithSettings(clickhouse.Settings{
			"max_execution_time": 3,      // server stops the work too
			"max_result_rows":    10_000, // a bug cannot return a million rows
			"log_comment":        "api.TopPages",
		}),
	)

	rows, err := r.conn.Query(ctx, `
		SELECT url, sum(views) AS views
		FROM shop.page_views_hourly
		WHERE tenant_id = {tenant:UInt32}
		  AND hour >= {from:DateTime} AND hour < {to:DateTime}
		GROUP BY url
		ORDER BY views DESC
		LIMIT {lim:UInt32}`)
	if err != nil {
		return nil, err
	}
	defer rows.Close()

	out := make([]PageStat, 0, limit)
	for rows.Next() { // streams blocks; does not load everything first
		var p PageStat
		if err := rows.Scan(&p.URL, &p.Views); err != nil {
			return nil, err
		}
		out = append(out, p)
	}
	return out, rows.Err()
}
Do
  • Select only the columns you need; a columnar store reads each named column from disk
  • Validate and clamp time ranges in the handler (for example max 90 days)
  • Use conn.Select(ctx, &dest, q) for small results, Query + Next for large ones
Don't
  • SELECT * from wide tables
  • Build SQL with fmt.Sprintf from request values
  • Rely only on the HTTP server's timeout; the query keeps running on ClickHouse

10. Serve dashboards from rollups

The rule

If a chart runs the same aggregation on every page load, compute it once at insert time with a materialized view and query the small table.

A materialized view in ClickHouse is an insert trigger: each block inserted into events is aggregated and written into the target table. The API then scans thousands of rows instead of billions.

CREATE TABLE shop.page_views_hourly
(
    tenant_id UInt32,
    hour      DateTime,
    url       String,
    views     SimpleAggregateFunction(sum, UInt64),
    users     AggregateFunction(uniq, UInt64)
)
ENGINE = AggregatingMergeTree
PARTITION BY toYYYYMM(hour)
ORDER BY (tenant_id, hour, url);

CREATE MATERIALIZED VIEW shop.page_views_hourly_mv TO shop.page_views_hourly AS
SELECT tenant_id, toStartOfHour(event_time) AS hour, url,
       count() AS views, uniqState(user_id) AS users
FROM shop.events
WHERE event_type = 'page_view'
GROUP BY tenant_id, hour, url;

-- App query: always re-aggregate, because rows for one key may not be merged yet
SELECT url, sum(views) AS views, uniqMerge(users) AS users
FROM shop.page_views_hourly
WHERE tenant_id = 42 AND hour >= now() - INTERVAL 7 DAY
GROUP BY url ORDER BY views DESC LIMIT 20;

Do this now: sort system.query_log by total read_rows grouped by normalized_query_hash. The top three are your rollup candidates.

11. Enforce tenant isolation in two layers

The rule

The tenant ID comes from the authenticated identity, is always a bound parameter, and is backed by a server-side guard.

Layer 1, the app: make it impossible to build a query without a tenant. A small type does this.

// TenantScope can only be created from a verified token, so repositories cannot forget the filter.
type TenantScope struct{ id uint32 }

func ScopeFromClaims(c Claims) (TenantScope, error) {
	if c.TenantID == 0 {
		return TenantScope{}, errors.New("no tenant in token")
	}
	return TenantScope{id: c.TenantID}, nil
}

func (s TenantScope) Params(extra clickhouse.Parameters) clickhouse.Parameters {
	p := clickhouse.Parameters{"tenant": strconv.FormatUint(uint64(s.id), 10)}
	maps.Copy(p, extra)
	return p
}

Layer 2, the server: a quota per API user stops one noisy tenant (or bug) from starving others; for untrusted query surfaces add a row policy so even a missing filter cannot leak rows.

-- Cap what the API user can do per hour
CREATE QUOTA api_hourly FOR INTERVAL 1 HOUR MAX queries = 100000, read_rows = 50000000000 TO api_reader;

-- Strongest isolation: one ClickHouse user per tenant with a row policy
CREATE ROW POLICY tenant_42 ON shop.events USING tenant_id = 42 TO tenant_42_user;

12. Separate users per workload

The rule

Ingest, API and ad-hoc analysts each get their own ClickHouse user and settings profile, and your service holds one pool per user it needs.

Lanes on a motorway. Trucks (ingest), cars (API) and the occasional oversized load (an analyst's year-long scan) share the road, but each lane has its own speed limit so one cannot block the others.
CREATE SETTINGS PROFILE api_profile SETTINGS
    readonly = 1, max_execution_time = 5, max_memory_usage = 4000000000,
    max_threads = 8, max_result_rows = 100000;
CREATE SETTINGS PROFILE ingest_profile SETTINGS
    max_insert_threads = 4, async_insert = 0;
CREATE SETTINGS PROFILE adhoc_profile SETTINGS
    readonly = 1, max_execution_time = 300, max_memory_usage = 20000000000, priority = 10;

CREATE USER api_reader     IDENTIFIED WITH sha256_password BY '...' SETTINGS PROFILE 'api_profile';
CREATE USER ingest_writer  IDENTIFIED WITH sha256_password BY '...' SETTINGS PROFILE 'ingest_profile';
GRANT SELECT ON shop.* TO api_reader;
GRANT INSERT ON shop.events TO ingest_writer;
// A service that both reads and writes keeps two pools with different credentials.
type Stores struct {
	Read  driver.Conn // api_reader: readonly, short timeouts
	Write driver.Conn // ingest_writer: INSERT only
}

Load passwords from a secret manager or environment at startup, never from source. Rotate by creating the new credential, deploying, then dropping the old one.

13. Cache and coalesce repeated queries

The rule

Round time ranges so identical dashboards produce identical cache keys, and collapse concurrent identical queries into one.

Ten users opening the same dashboard at 09:00 should cause one ClickHouse query, not ten. Rounding "last 24 hours" to the minute makes the key repeat; singleflight merges requests that arrive together.

var group singleflight.Group

func (s *Service) TopPagesCached(ctx context.Context, t TenantScope, window time.Duration) ([]PageStat, error) {
	to := time.Now().UTC().Truncate(time.Minute) // same key for a whole minute
	from := to.Add(-window)
	key := fmt.Sprintf("top:%d:%d:%d", t.id, from.Unix(), to.Unix())

	if v, ok := s.cache.Get(key); ok {
		return v.([]PageStat), nil
	}
	v, err, _ := group.Do(key, func() (any, error) {
		res, err := s.repo.TopPages(ctx, t.id, from, to, 20)
		if err == nil {
			s.cache.Set(key, res, time.Minute)
		}
		return res, err
	})
	if err != nil {
		return nil, err
	}
	return v.([]PageStat), nil
}

ClickHouse also has a server-side query cache (use_query_cache=1). It helps across services but is per server and does not see your app's notion of freshness; an app cache is usually the first lever.

14. Paginate with keysets, not OFFSET

The rule

Page through results by remembering the last sort key, and order by columns that match the table's sorting key.

LIMIT 50 OFFSET 100000 makes ClickHouse produce and discard 100,000 rows on every page. A keyset cursor reads only the next 50, and when it follows the sorting key ClickHouse can stop early.

const pageQuery = `
SELECT event_time, user_id, event_type, url
FROM shop.events
WHERE tenant_id = {tenant:UInt32}
  AND (event_time, user_id) < ({cur_time:DateTime64(3)}, {cur_user:UInt64})
ORDER BY event_time DESC, user_id DESC
LIMIT 50`

// Cursor is opaque to clients: base64 of the last row's (event_time, user_id).
type Cursor struct {
	Time time.Time `json:"t"`
	User uint64    `json:"u"`
}

15. Versioned, additive schema migrations

The rule

Schema changes are versioned files applied by a migration job before the new app version rolls out, and every change is backward compatible with the running version.

  1. Add, don't change. ADD COLUMN with a DEFAULT is instant (metadata only). Changing a column's type rewrites data.
  2. Expand, then contract. Deploy code that writes both old and new columns, backfill, switch reads, then drop the old column in a later release.
  3. On a cluster, use ON CLUSTER (or a Replicated database) so every node gets the DDL.
  4. Name explicit insert columns in Go (INSERT INTO t (a, b, c)) so adding a column never breaks a running writer.
-- migrations/0007_add_referrer.up.sql
ALTER TABLE shop.events ON CLUSTER prod
    ADD COLUMN IF NOT EXISTS referrer LowCardinality(String) DEFAULT '';

Tools like golang-migrate (has a ClickHouse driver) or goose track applied versions. Run them as a CI step or a Kubernetes Job, not from every app pod at startup, so two pods never race.

16. Test against a real ClickHouse

The rule

Integration tests run your real SQL against a real ClickHouse container with the same major version as production.

SQL mocks cannot tell you that a function does not exist, a type does not cast, or a materialized view produces wrong totals. Testcontainers starts a throwaway server per test package.

import (
	"github.com/ClickHouse/clickhouse-go/v2"
	tcch "github.com/testcontainers/testcontainers-go/modules/clickhouse"
)

func TestTopPages(t *testing.T) {
	ctx := context.Background()
	ctr, err := tcch.Run(ctx, "clickhouse/clickhouse-server:25.8",
		tcch.WithUsername("test"), tcch.WithPassword("test"), tcch.WithDatabase("shop"),
		tcch.WithInitScripts("../../migrations/0001_init.up.sql"),
	)
	if err != nil {
		t.Fatal(err)
	}
	t.Cleanup(func() { _ = ctr.Terminate(ctx) })

	addr, _ := ctr.ConnectionHost(ctx)
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{addr}, Auth: clickhouse.Auth{Database: "shop", Username: "test", Password: "test"},
	})
	if err != nil {
		t.Fatal(err)
	}

	// insert fixture events, then assert on what the repository returns
	repo := &Repo{conn: conn}
	got, err := repo.TopPages(ctx, 42, time.Now().Add(-time.Hour), time.Now(), 10)

Testing rollups: insert into the raw table, then query the rollup with the same re-aggregation the app uses. Do not call OPTIMIZE FINAL in tests to "fix" duplicates; the app must handle unmerged rows.

17. Tag queries so you can trace them

The rule

Every query carries a log_comment naming the code path and a query_id you also log. Then system.query_log becomes your per-endpoint profiler.

-- Which endpoints cost the most in the last day?
SELECT log_comment,
       count()                                   AS calls,
       quantile(0.95)(query_duration_ms)         AS p95_ms,
       formatReadableQuantity(sum(read_rows))    AS rows_read,
       formatReadableSize(max(memory_usage))     AS peak_mem
FROM system.query_log
WHERE type = 'QueryFinish' AND event_time > now() - INTERVAL 1 DAY
  AND user = 'api_reader'
GROUP BY log_comment
ORDER BY sum(read_rows) DESC;

Pair this with app metrics: flush latency, batch size, buffer depth, rows inserted, query errors by code. If you use OpenTelemetry, clickhouse.WithSpan(span.SpanContext()) passes the trace context to the server so its spans join your trace.

18. Health checks and graceful shutdown

The rule

Readiness checks are cheap and bounded; shutdown finishes the current batch before closing connections.

// Readiness: a ping with a short timeout. Never run a real query in a probe.
func (s *Server) ready(w http.ResponseWriter, r *http.Request) {
	ctx, cancel := context.WithTimeout(r.Context(), 500*time.Millisecond)
	defer cancel()
	if err := s.ch.Ping(ctx); err != nil {
		http.Error(w, "clickhouse unavailable", http.StatusServiceUnavailable)
		return
	}
	w.WriteHeader(http.StatusOK)
}

func main() {
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()

	cfg := loadConfig()
	conn := must(NewClickHouse(ctx, cfg))
	nc := must(nats.Connect(cfg.NatsURL, nats.Name("clickhouse-ingest")))
	js := must(jetstream.New(nc))
	cons := must(setupStream(ctx, js))
	ing := &Ingester{conn: conn, cons: cons, maxRows: 50_000, maxWait: time.Second}

	done := make(chan struct{})
	go func() { ing.Run(ctx); close(done) }()

	<-ctx.Done() // SIGTERM: Run stops fetching after the current batch
	<-done       // last batch inserted and acked
	_ = nc.Drain()
	_ = conn.Close()
}

Set the Kubernetes terminationGracePeriodSeconds longer than your fetch wait plus the worst retry time. If a pod is killed anyway, nothing is lost: its unacked messages are redelivered to another pod after AckWait.
