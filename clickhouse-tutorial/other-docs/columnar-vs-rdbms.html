Columnar databases vs traditional RDBMS

A guide to why ClickHouse (a columnar database) exists next to Postgres/MySQL (row-oriented RDBMS), when each wins, the pitfalls of going columnar, and a decision process you can reuse. Examples use the tutorial's ShopStream data (shop.events: 10M tracking events, 10 columns; see data/README.md).

Row-oriented vs column-oriented

  • Row store: each row's values sit together in a page (8 KB in Postgres). Reading one row is one page read; reading one column means reading every page.
  • Column store: each column is its own file, sorted by the table's ORDER BY. Reading one column touches one file; reading one full row means opening every file. Sorting puts equal values next to each other (see tenant_id).

2. Benefits of columnar, with examples

Benefit 1 — Read only the columns you need (I/O reduction)

Example. "Revenue per country last month" needs event_time, country, revenue: 3 of 10 columns.

Row storeColumn store
Data read for 10M events (~620 MB uncompressed)~620 MB (all columns)~160 MB uncompressed, ~70 MB compressed
Wide tables (100+ columns, common in analytics)worse: still reads allsame: still reads 3

The wider the table, the bigger the win. Analytics tables tend to be wide ("every attribute of the event"), and queries tend to use few columns.

Benefit 2 — Much better compression

Compression works by finding repetition. A column store helps it in two ways.

1. One column holds one kind of value. A row page mixes a timestamp, a number, a UUID and some text, so there is little repetition to find. A column file holds only country codes, or only tenant ids, which repeat a lot.

2. Sorting puts equal values next to each other. ClickHouse stores rows sorted by the table's ORDER BY. ShopStream sorts by tenant_id first, so all of a shop's rows sit together:

Why this matters: a repeated value costs almost nothing to store. 1 × 4 is two small numbers, however long the run is.

Going further with codecs

ClickHouse also provides codecs: special encodings you can turn on per column to make compression even better, for example for timestamps or numbers. See Understanding Compression Codecs (understanding_codecs.html) to learn more.

Why it matters: better compression means less disk space to pay for, and faster queries, because there is less data to read.

Benefit 3 — Vectorised execution

Modern CPUs can do the same calculation on several values at once, in a single step. This is called SIMD ("single instruction, multiple data"). Because a column stores the same kind of value side by side, ClickHouse can hand the CPU a whole group of values and process them together, instead of one by one. Benefit 4 — Sparse primary index that fits in memory

ClickHouse keeps the table sorted by its ORDER BY columns, then splits it into blocks of 8,192 rows called granules. For each block it writes down just one thing: the first value in it. That list is the index.

Because it has only one entry per 8,192 rows, the index is very small. For 10 million rows it has about 1,200 entries, so it always fits in memory. When a query filters on the sort column, ClickHouse checks the index, works out which blocks could contain a match, and reads only those.

Real example from Lesson 01: finding shop 42's events for one week read 5 of 422 blocks, about 40,000 rows out of 3.4 million in that month.

Compared with a normal database: Postgres or MySQL keep one index entry for every row. The index finds the matching rows too, but then the database has to jump to each row's location on disk one at a time. ClickHouse instead reads a few whole blocks straight through, which is much faster for large amounts of data.

Benefit 5 — Parallelism and scale-out built in

A big query is split into many small jobs that run at the same time.

Inside one server, the data is already cut into blocks (the granules from Benefit 4). ClickHouse gives different blocks to each CPU core. Every core adds up its own blocks, and at the end the small totals are combined. An 8-core machine works on 8 blocks at once instead of one.

Across servers, you can split the data over several machines (shards). A Distributed table (Lesson 06) sends your query to every server, each one scans only its own share, and the small results are merged into one answer.

Why it matters: when data grows, you add servers instead of buying a bigger one. Two servers scan roughly twice as much data in the same time. A typical Postgres query runs on one server and often on only a few cores.

Benefit 6 — Precomputation at insert time

Materialized views turn raw events into rollups as data arrives (Lesson 04). The ShopStream dashboard reads the per-minute rollup (a fraction of the raw data) and stays fast as history grows.

3. Where the row store still wins

Columnar is great for questions over many rows. For work on one record at a time, a normal database like Postgres or MySQL is the better tool.

If you need…Why a row store is better
Moving money or reserving stockYou need all-or-nothing changes across several rows (transactions). If one step fails, everything is undone. ClickHouse does not offer this.
Changing single rows oftenA row store edits the row where it sits. ClickHouse has to rewrite a whole chunk of each column to change one value.
Fetching one record by idA row store reads one place. ClickHouse reads a piece from every column file (see the diagram).
Enforcing rules like "email must be unique"A row store can reject bad data. In ClickHouse the key only sets the sort order, so duplicates are allowed.
Lots of tiny writesA row store handles thousands of one-row saves a second. ClickHouse wants rows sent in batches.
Joining many small tablesRow stores are built for this. ClickHouse works best when data is already combined into one wide table.

This is why an app's main data (accounts, orders, payments) usually stays in Postgres.

4. Common mistakes and how to avoid them

Most problems with ClickHouse come from using it the way you would use Postgres. The biggest one is sending rows one at a time:

MistakeWhat goes wrongWhat to do insteadLesson
Sending rows one at a timeEvery insert creates a new part on disk. Too many and ClickHouse falls behind and refuses writes.Send rows in batches (thousands at a time, about once a second), turn on async inserts, or put Kafka in front.03
Using UPDATE and DELETE like in PostgresEach change rewrites large chunks of data. It is slow and piles up.Insert a new version of the row instead, using ReplacingMergeTree. Remove old data with TTL or by dropping partitions.04
Picking the wrong sort orderThe index can't skip anything, so every query reads the whole table.Sort by the column you filter on most, with time last. Check with EXPLAIN indexes = 1.02
Using SELECT *It reads every column file, which throws away the main benefit.Ask only for the columns you need.01
Expecting no duplicatesA retried insert can store the same rows twice.Make inserts safe to retry (insert_deduplication_token), or use ReplacingMergeTree.03, 05
Big joins between many tablesThe right-hand table is loaded into memory. Big joins are slow or run out of memory.Combine data when you load it, use dictionaries for small lookup tables, and put the smaller table on the right.04, 06
Too many partitionsThousands of tiny parts make startup and merging slow.Partition by month (or by day for very large data). Never partition by user or customer.02
Nullable columns and oversized typesExtra files and wasted space.Use default values instead of NULL, use the smallest type that fits, and use LowCardinality for repeated text.02
Reading rollup tables without GROUP BYThe same key can show up in several rows until background merges finish.Always GROUP BY (with -Merge functions) when reading rollups.04
Reading straight after writing on another serverThe other copy may not have the new row yet.Use insert_quorum, or keep a user's session on one server.05
One heavy query slowing everyoneA single ad-hoc query can use all the memory and CPU.Set memory and time limits, and quotas per user.03, 10
Treating copies as a backupA mistaken DROP is copied to every server too.Keep backups outside the cluster and test restoring them.07

5. How to decide: columnar or RDBMS?

Step 1: Answer a few questions about how the data is used

Think about what your queries do, not what the data looks like.

6. The usual answer: use both

Most teams don't pick one. They use each database for what it is good at.

  • Postgres keeps the important records (customers, orders, money) and stays the source of truth.
  • ClickHouse keeps events and a copy of the records for reports and dashboards.
  • A sync tool (CDC, such as Debezium, PeerDB or ClickPipes) copies changes from Postgres to ClickHouse automatically.

Simple rule: if the question is "how many, how much, over time", use ClickHouse. If it is "this one record, exactly right, right now", use Postgres.
