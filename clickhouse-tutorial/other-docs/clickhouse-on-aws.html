Deploying ClickHouse on AWS: ECS and Kubernetes

This document describes how to run the same production layout as the tutorial cluster (2 shards × 2 replicas + 3 Keeper nodes, Lessons 05–07) on AWS. It covers two options: Amazon ECS and Kubernetes (Amazon EKS). It explains how the deployment should be structured, what to configure for security, what an external application needs, and which sidecars help with resilience. It is a design guide, not click-by-click instructions.

ECS or EKS

This document shows two ways to run the same ClickHouse cluster on AWS: on Amazon ECS (section 1) and on Amazon EKS (section 2). Whichever you choose, many decisions are the same: the kind of machines, the disks, how copies are spread, how config is managed, backups and monitoring. The table below lists those shared decisions once, so sections 1 and 2 only cover what is specific to each platform.

TopicRecommendationWhy
ComputeEC2 instances you control (ECS on EC2, or EKS managed node groups). Not Fargate.ClickHouse needs persistent, fast local disks and stable hosts. Fargate storage is tied to the task and is lost or recreated when the task moves.
Instance typeMemory-optimised with good network (r6i / r7i / r7g, 4xlarge to start). Separate small instances (m7g.large) for Keeper.ClickHouse uses RAM for aggregation and page cache. Keeper needs little CPU but low latency.
StorageEBS gp3 per replica, sized for 2× data + headroom; raise IOPS/throughput as needed. Encrypted with a KMS key. Optionally tier old data to S3 via a storage policy.EBS survives restarts and can be reattached in the same AZ. Replication handles AZ loss.

1. ClickHouse on Amazon ECS

Architecture

How the deployment is structured

The numbers match the markers in the diagram above. The parts fall into three layers.

Layer 1Ingress and network access

Public traffic terminates at an internet-facing ALB in the public subnets. The application runs as an ECS service in private subnets and reaches ClickHouse only through an internal NLB inside the VPC.

1Users on the internet. Customers only ever talk to the load balancer; nothing behind it is visible to them.

2Application Load Balancer. The only public part of the system. HTTPS with an ACM certificate and AWS WAF stop bad traffic before it reaches anything else.

3App tasks. Several copies of the app as one ECS service with auto scaling, so one crashing task does not take the app down.

4Internal NLB. One private address for the database, so the app never needs to know which ClickHouse task it talks to. It health-checks the ClickHouse tasks and skips any that are down.

Layer 2Compute and orchestration

An ECS cluster on EC2 in a single Availability Zone (us-east-1a), backed by one Auto Scaling group of three hosts in a spread placement group. ECS services with desiredCount 1 pin each ClickHouse replica and Keeper node to its host; Cloud Map gives each a stable DNS name.

5ECS cluster on EC2, us-east-1a. All database hosts sit in one zone, which keeps replica-to-replica traffic fast and free of cross-zone charges. The trade-off: a zone outage stops the cluster, so S3 backups are the recovery plan.

6EC2 hosts 1, 2 and 3. A spread placement group puts each host on different physical hardware. Hosts 1 and 2 each carry one full copy of the data; host 3 carries the third Keeper so Keeper always keeps a majority.

Layer 3Data and storage

A 2-shard × 2-replica ReplicatedMergeTree cluster coordinated by a 3-node Keeper (Raft) ensemble. Each task is backed by its own KMS-encrypted gp3 EBS volume mounted at /var/lib/clickhouse.

7ClickHouse tasks s1r1, s1r2, s2r1, s2r2. Each host runs one replica of each shard, never both copies of the same shard, so losing a host still leaves a full copy. Each task has a fixed memory limit so two tasks on one host cannot starve each other.

8Keeper tasks 1, 2 and 3. One Keeper per host keeps the copies in step. Keeper needs 2 of 3 to work, so any one host can fail safely.

9EBS disks. Every task has its own encrypted disk. When a host is replaced, the volume is attached to the new host, so the data survives.

EC2 Configurations

The data is stored as 2 shards (each holding roughly half the rows) with 2 replicas (identical copies) of each. The three EC2 hosts are arranged so that every host holds one copy of each shard, and never both copies of the same shard:

EC2 hostRunsHolds
Host 1ClickHouse s1r1, ClickHouse s2r1, Keeper 1Copy A of shard 1 + copy A of shard 2 = one full copy of the data
Host 2ClickHouse s1r2, ClickHouse s2r2, Keeper 2Copy B of shard 1 + copy B of shard 2 = a second full copy
Host 3Keeper 3 (plus spare room)No table data; keeps Keeper at 3 nodes so it always has a majority

This layout gives two things. If host 1 or host 2 fails, the other still has the complete data set and keeps answering queries. And because both hosts carry ClickHouse servers, both do work on every query instead of one sitting idle as a standby.

Running two ClickHouse servers on one host means they share its CPU and memory, so each one needs limits. Give each ClickHouse task a fixed memory limit in its ECS task definition of about 45% of the host (for example about 58 GB each on a 128 GB host), leaving the rest for the operating system, and give each its own EBS volume. Without the memory limit, one heavy query on s1r1 could use all the RAM and get s2r1 killed as well.

To grow later, you can move from 4 ClickHouse servers on 2 hosts to 4 hosts with one server each, or add more shards. Whatever the layout, keep one rule: the two copies of a shard are never on the same host (s1r1 apart from s1r2, s2r1 apart from s2r2). Otherwise a single host failure would lose both copies of that shard.

The role of Keeper

ClickHouse Keeper is a small coordination service (ClickHouse's built-in replacement for ZooKeeper). It stores no table data. It keeps the shared notebook that the replicas use to agree on what has happened:

  • the list of data parts each table should have, and which replica has them;
  • the queue of work each replica still has to do (fetch a new part, run a merge, apply a change);
  • insert IDs used to throw away duplicate inserts when a client retries;
  • the queue of ON CLUSTER commands (CREATE, ALTER) so every server applies them.

There are three Keeper nodes, one per host, because Keeper only accepts changes when a majority (2 of 3) agree. Lose any one host and the other two still form a majority. With only two Keeper nodes, losing one would stop all writes.

What if a Keeper node fails?

No ClickHouse server depends on the Keeper running on its own host. The three Keeper nodes work as one service and each holds a full copy of the same to-do list. Every ClickHouse server is configured with the addresses of all three and talks to whichever one answers.

One Keeper node down (for example Keeper 2 on host 2):

  1. Keeper 1 and Keeper 3 are still running. That is 2 of 3, a majority, so the to-do list keeps working.
  2. If s1r2 was connected to Keeper 2, it loses that connection and reconnects to Keeper 1 or 3 on its own, usually within seconds.
  3. s1r2 reads the same list there, sees the new part and downloads it from s1r1 as normal. Inserts and queries carry on.
  4. When Keeper 2 comes back, it copies what it missed from the other two and rejoins.

Two Keeper nodes down at the same time: there is no majority, so replicated tables become read-only. Queries still work, but inserts fail until a second Keeper node is back. No data is lost, because the data lives on the ClickHouse replicas and Keeper only holds the to-do list. This is why each Keeper node runs on a separate host.

How data stays in sync

  1. The app sends rows to the Distributed table through the internal NLB. ClickHouse uses the sharding key to send each row to shard 1 or shard 2.
  2. One replica of that shard (say s1r1) writes the rows to disk as a new part and records it in Keeper.
  3. The other replica (s1r2) watches Keeper, sees the new entry, and downloads the part from s1r1. Now both copies match.
  4. Background merges are recorded the same way, so both replicas end up with identical parts.
  5. If a replica was down, it reads what it missed from Keeper when it comes back and catches up on its own.

ECS specifics to watch

  • Set container ulimits nofile 262144 and enough memory reservation; set max_server_memory_usage_to_ram_ratio below the task limit.
  • Stop timeout of 120 s or more so ClickHouse can flush and shut down cleanly.
  • ECS will not stop two ClickHouse replicas at once only if you deploy services one by one; automate that order in your pipeline.

2. ClickHouse on Amazon EKS

Architecture

How the deployment is structured

The numbers match the markers in the diagram above. The parts fall into three layers.

Layer 1 Ingress and network access

Public traffic terminates at an internet-facing ALB in the public subnets. The application runs in private subnets and reaches ClickHouse only through an internal NLB inside the VPC.

1Users on the internet. Customers only ever talk to the load balancer; nothing behind it is visible to them.

2Application Load Balancer. The only public part of the system. HTTPS and AWS WAF stop bad traffic before it reaches anything else.

3App tasks. Several copies of the app, so one crashing does not take the app down; auto scaling adds copies under load.

4Internal NLB. One private address for the database, so the app never needs to know which ClickHouse pod it talks to. Nothing outside the VPC can reach it.

Layer 2 Compute and orchestration

An EKS cluster with dedicated managed node groups across three Availability Zones. The ClickHouse Operator reconciles the desired state (CHI/CHK) into StatefulSets, Services and ConfigMaps.

5EKS cluster, namespace clickhouse. All database parts live in their own namespace, so their permissions and network rules are kept apart from anything else.

6ClickHouse Operator. You describe the cluster in two files and the operator builds and repairs everything below, so no pod or disk is created by hand.

7Availability Zones a, b, c. The two copies of a shard sit in different zones (separate data centres), so a whole zone can fail and the data is still there.

8ClickHouse node group. One ClickHouse pod per EC2 machine, so pods never fight over memory and losing a machine loses only one copy.

Layer 3 Data and storage

A 2-shard × 2-replica ReplicatedMergeTree cluster coordinated by a 3-node Keeper (Raft) ensemble. Each pod is backed by its own KMS-encrypted gp3 EBS volume provisioned through the EBS CSI driver.

9ClickHouse pods s1r1, s1r2, s2r1, s2r2. The data is split into 2 shards to share the work, and each shard has 2 copies so no single failure loses data. Only one pod is restarted at a time.

10Keeper pods 1, 2, 3. Three Keeper pods, one per zone on small machines of their own, keep the copies in step. They need 2 of 3 to work, so one can fail safely.

11EBS disks. Every pod has its own encrypted disk. When a pod restarts, the same disk is reattached, so nothing is lost.

The ClickHouse operator (EKS only)

What an operator is. Kubernetes knows how to run containers, but not how to run a ClickHouse cluster: which pod is which shard, how to write remote_servers, or how to upgrade without losing data. An operator is a program running inside the cluster that adds that knowledge. You describe the cluster you want in one YAML file; the operator creates everything and keeps it that way. If a pod or setting drifts, it puts it back. This is what ECS does not have, and why on ECS you write items 1 to 4 of the config yourself.

Which operator. The Altinity ClickHouse Operator is open source (Apache 2.0) and the most widely used. It adds two new resource types to Kubernetes:

ResourceWhat the operator creates from it
ClickHouseInstallation (CHI)One StatefulSet per replica (4 here), one Service per replica, a Service for the whole cluster, the ConfigMaps with config.xml/users.xml, and one PVC (EBS volume) per replica
ClickHouseKeeperInstallation (CHK)A StatefulSet with 3 Keeper pods, their volumes, and a Service the ClickHouse pods connect to

Install it and apply the two files:

helm repo add altinity https://helm.altinity.com
helm install clickhouse-operator altinity/altinity-clickhouse-operator \
  --namespace clickhouse-operator --create-namespace

kubectl apply -f keeper.yaml        # the ClickHouseKeeperInstallation
kubectl apply -f clickhouse.yaml    # the ClickHouseInstallation
kubectl get chi,chk -n clickhouse   # status: Completed when everything is up

The Keeper ensemble (keeper.yaml):

apiVersion: clickhouse-keeper.altinity.com/v1
kind: ClickHouseKeeperInstallation     # "I want a Keeper ensemble"
metadata:
  name: shopstream
  namespace: clickhouse
spec:
  configuration:
    clusters:
      - name: keeper
        layout:
          replicasCount: 3             # 3 nodes = survives losing 1

The ClickHouse cluster (clickhouse.yaml). This one file replaces most of the hand-written config in section 3. The comments show which config item each part covers:

apiVersion: clickhouse.altinity.com/v1
kind: ClickHouseInstallation          # "I want a ClickHouse cluster"
metadata:
  name: shopstream
  namespace: clickhouse
spec:
  configuration:
    zookeeper:                         # item 1: where Keeper is
      nodes:
        - host: keeper-shopstream      # service created by the CHK below
          port: 2181
    clusters:
      - name: prod                     # item 4: cluster layout
        layout:
          shardsCount: 2
          replicasCount: 2
    users:                             # items 6-7: users and profiles
      app_writer/password_sha256_hex: "<sha256 of the password>"
      app_writer/profile: app_writer_profile
      app_writer/networks/ip: "10.0.0.0/16"
    profiles:
      app_writer_profile/insert_quorum: 2
  defaults:
    templates:
      podTemplate: clickhouse
      dataVolumeClaimTemplate: data
  templates:
    podTemplates:
      - name: clickhouse
        podDistribution:
          - type: ReplicaAntiAffinity   # two copies of a shard never on the same node
        spec:
          containers:
            - name: clickhouse
              image: clickhouse/clickhouse-server:25.8
              resources:
                requests: { cpu: "8", memory: 56Gi }
                limits:   { memory: 56Gi }
    volumeClaimTemplates:
      - name: data                       # one EBS volume per replica
        spec:
          storageClassName: gp3-encrypted
          accessModes: [ReadWriteOnce]
          resources:
            requests: { storage: 500Gi }

What the operator does for you:

  • Writes the config. It generates the Keeper addresses, the remote_servers layout and a unique {shard}/{replica} macro for every pod, so items 1 to 4 of section 3 are not written by hand.
  • Creates storage. Each replica gets its own EBS volume through the StorageClass. If a pod restarts or moves, it gets the same volume back.
  • Rolling upgrades. Change the image version in the CHI and apply it; the operator restarts one replica at a time and waits for each to be healthy before the next.
  • Scaling. Change shardsCount or replicasCount. For a new replica, the operator creates the tables on it and replication copies the data over. For a new shard, it creates the tables; existing data stays where it is and new rows spread over all shards.
  • Config changes. Edit the CHI (for example a new user or profile setting) and apply it; the operator updates the files on every pod.

Things to watch:

  • Keep the operator version and the CHI/CHK examples in its documentation in step; field names can change between operator releases.
  • Deleting a CHI deletes its StatefulSets. Use a StorageClass with reclaimPolicy: Retain so the EBS volumes survive a mistake, and keep backups anyway.
  • The operator itself is a single pod. If it is down, the running ClickHouse cluster keeps working; only changes wait until it is back.
  • Passwords in the CHI should come from Kubernetes Secrets (filled from AWS Secrets Manager with External Secrets), not plain text.

Docs: Altinity ClickHouse Operator on GitHub (see its docs/ folder for CHI and CHK examples).

Kubernetes specifics to watch

  • Never let the StatefulSet be deleted with its PVCs; keep Retain and back up anyway.
  • Memory limits must be above what ClickHouse thinks it can use; otherwise the kernel kills the pod (OOMKilled) mid-query.
  • Keep Keeper in its own pods, never as an extra container inside a ClickHouse pod. In the diagram each AZ has a Keeper pod next to the ClickHouse pods: it shares the zone, but it is a separate pod on the small Keeper node group, so it keeps running if a ClickHouse pod restarts.

On EKS the operator writes most of items 1 to 4 for you; on ECS you write them yourself. The examples below show the plain ClickHouse files.

This is the configuration that keeps the copies in sync. Items 1 to 4 go in files under /etc/clickhouse-server/config.d/ on every server (baked into the image or loaded at start). Item 2 is the only one that differs per server.

1. Where Keeper is (every ClickHouse server). List all three Keeper nodes so a server can switch to another one if its current Keeper fails.

<clickhouse>
  <zookeeper>
    <node><host>keeper-1.ch.internal</host><port>9181</port></node>
    <node><host>keeper-2.ch.internal</host><port>9181</port></node>
    <node><host>keeper-3.ch.internal</host><port>9181</port></node>
    <session_timeout_ms>30000</session_timeout_ms>
  </zookeeper>
</clickhouse>

Why Keeper also has an EBS disk.

Keeper does not store your table rows, but it does keep its own small amount of data on disk:

  • a log of every change it records (new parts, merges, schema changes, insert IDs used for deduplication);
  • regular snapshots of the full to-do list.

Keeper only confirms a change once a majority of nodes have written it to disk. If a Keeper node restarted with an empty disk, it would forget changes it had already confirmed, and the replicas could lose track of which parts they should have. So each Keeper node needs a disk that survives restarts. It is small: a few GB of data, so a 20 to 50 GB gp3 volume is plenty (ClickHouse disks hold hundreds of GB). The Keeper config points at that disk:

<clickhouse>
  <keeper_server>
    <tcp_port>9181</tcp_port>
    <server_id>1</server_id>   <!-- 1, 2 or 3: different on each Keeper node -->
    <log_storage_path>/var/lib/clickhouse/coordination/log</log_storage_path>            <!-- on the EBS volume -->
    <snapshot_storage_path>/var/lib/clickhouse/coordination/snapshots</snapshot_storage_path> <!-- on the EBS volume -->
    <raft_configuration>
      <server><id>1</id><hostname>keeper-1.ch.internal</hostname><port>9234</port></server>
      <server><id>2</id><hostname>keeper-2.ch.internal</hostname><port>9234</port></server>
      <server><id>3</id><hostname>keeper-3.ch.internal</hostname><port>9234</port></server>
    </raft_configuration>
  </keeper_server>
</clickhouse>

On EKS the operator writes this from the ClickHouseKeeperInstallation and creates the volume; on ECS it goes in the Keeper image and the volume is mounted at /var/lib/clickhouse.

2. Who am I (different on each server). Macros give each server its shard and replica name. They are filled into the table paths below, so s1r1 and s1r2 find the same entry in Keeper. On ECS, set them from task environment variables.

<clickhouse>
  <macros>
    <cluster>prod</cluster>
    <shard>1</shard>          <!-- 1 or 2 -->
    <replica>s1r1</replica>   <!-- s1r1, s1r2, s2r1, s2r2 -->
  </macros>
</clickhouse>

3. How replicas reach each other to copy parts. Each server tells the others the address to download parts from. Use its Cloud Map name, and the same credentials on all servers.

<clickhouse>
  <interserver_http_host from_env="CH_HOSTNAME"/>   <!-- e.g. s1r1.ch.internal -->
  <interserver_http_port>9009</interserver_http_port>
  <interserver_http_credentials>
    <user>interserver</user>
    <password from_env="CH_INTERSERVER_PASSWORD"/>
  </interserver_http_credentials>
</clickhouse>

4. The cluster layout. Lists which servers hold which shard. internal_replication = true is important: the Distributed table writes to one replica only, and replication copies it to the other. With false, both copies are written separately and can drift apart.

<clickhouse>
  <remote_servers>
    <prod>
      <shard>
        <internal_replication>true</internal_replication>
        <replica><host>s1r1.ch.internal</host><port>9000</port></replica>
        <replica><host>s1r2.ch.internal</host><port>9000</port></replica>
      </shard>
      <shard>
        <internal_replication>true</internal_replication>
        <replica><host>s2r1.ch.internal</host><port>9000</port></replica>
        <replica><host>s2r2.ch.internal</host><port>9000</port></replica>
      </shard>
    </prod>
  </remote_servers>
</clickhouse>

5. The tables: one stores the data, one is used by the application.

With 2 shards, every server holds only part of the data, so you need two tables that work together:

TableEngineWhat it doesWho uses it
shop.events_localReplicatedMergeTreeStores the rows on disk. Each server holds only its own shard. Keeps the two copies of a shard in sync through Keeper.ClickHouse itself
shop.eventsDistributedStores nothing. Sends each inserted row to the right shard, and sends each query to both shards and combines the results.The application

A table can only have one engine, and two tables cannot share a name in the same database, so they get different names. _local is just a naming habit. If you prefer the same name, put them in different databases (for example shop_local.events and shop.events).

-- Table 1: stores the rows (created on all 4 servers)
CREATE TABLE shop.events_local ON CLUSTER prod
(
    event_time DateTime,
    shop_id    UInt32,
    user_id    UInt64,
    event_type LowCardinality(String),
    revenue    Decimal(10,2)
)
ENGINE = ReplicatedMergeTree(
    '/clickhouse/tables/{shard}/shop/events_local',  -- shared per shard
    '{replica}')                                       -- unique per copy
PARTITION BY toYYYYMM(event_time)
ORDER BY (shop_id, event_time);

-- Table 2: what the application uses (created on all 4 servers)
CREATE TABLE shop.events ON CLUSTER prod AS shop.events_local
ENGINE = Distributed(prod, shop, events_local, cityHash64(shop_id));

What each part means:

PartMeaning
ON CLUSTER prodRun the command on all four servers in the prod cluster, so both tables exist everywhere.
ReplicatedMergeTree(path, replica)Store rows and keep copies in sync. The path contains {shard}, so s1r1 and s1r2 share one to-do list in Keeper; {replica} gives each copy its own name. Both values come from the macros in item 2.
PARTITION BY / ORDER BYGroup data by month, and sort it by shop and time so queries for one shop read very little.
AS shop.events_localGive shop.events the same columns as the storage table.
Distributed(prod, shop, events_local, ...)Forward work to the prod cluster, into shop.events_local on each server.
cityHash64(shop_id)The sharding key. It turns the shop_id into a number that picks shard 1 or shard 2. All rows of one shop go to the same shard, and shops spread evenly.

What happens, with an example. The application records a page view for the shop whose shop_id is 42:

INSERT INTO shop.events (event_time, shop_id, user_id, event_type, revenue)
VALUES ('2026-10-01 10:00:00', 42, 1001, 'page_view', 0);
  1. shop.events reads the row's shop_id (42) and computes cityHash64(42). The result decides the shard; say it picks shard 1.
  2. The row is written into shop.events_local on one replica of shard 1 (s1r1).
  3. s1r1 records the new data in Keeper; s1r2 sees it and copies the data from s1r1. Both copies of shard 1 now have the row.
  4. Every later row with shop_id = 42 goes to shard 1 too. Rows for other shops land on shard 1 or 2 depending on their hash.

Now the application asks how many events shop 42 had:

SELECT count() FROM shop.events WHERE shop_id = 42;

shop.events sends the query to one replica of each shard, each counts its own rows, and the two counts are added into one answer. If the same query were run on shop.events_local on a shard 2 server, it would return 0, because shop 42's rows live on shard 1. That is why the application always uses shop.events.

6. Insert settings for the application (optional). The application logs in to ClickHouse with its own ClickHouse user (here called app_writer), just like an app logs in to Postgres with a database user. A profile is a named group of settings, and each user is linked to one profile. Every query that user runs automatically uses those settings, so the application does not have to set them itself. The settings below make inserts safe: an insert only succeeds once both copies of the shard have the data, and a retried insert is not stored twice. This goes in a file such as /etc/clickhouse-server/users.d/app.xml on every server.

<clickhouse>
  <!-- the group of settings -->
  <profiles>
    <app_writer_profile>
      <insert_quorum>2</insert_quorum>                     <!-- wait until both replicas have the data -->
      <insert_quorum_timeout>60000</insert_quorum_timeout> <!-- give up after 60 s -->
      <insert_deduplicate>1</insert_deduplicate>           <!-- ignore an identical retried insert -->
      <distributed_foreground_insert>1</distributed_foreground_insert> <!-- send rows to the shard now (old name: insert_distributed_sync) -->
    </app_writer_profile>
  </profiles>

  <users>

Is item 6 required? No. Items 1 to 5 are required: without them, replication and sharding do not work. Item 6 is optional. Replication keeps both copies in sync without it; these settings only add a stronger promise.

SettingWithout itWhen to use it
insert_quorum = 2An insert is confirmed once one replica has it; the other copies it a moment later. If that first server dies in between, those rows can be lost.Data you cannot lose (orders, payments). Can skip for clicks or page views.
insert_deduplicateAlready on by default for replicated tables.Listed only so you know it is there.
distributed_foreground_insertRows may wait on the receiving server and be sent to the shard in the background. Faster, but lost if that server crashes first.When every confirmed insert must already be on its shard.

The trade-off: these settings make each insert a little slower but safer. The separate user and profile are not required either; they are the tidy way to apply settings to one application. The application could also set them on its own connection instead.

ClickHouse guidance: Selecting an insert strategy (batching, async inserts, deduplication), Transactional (ACID) support (insert_quorum and durability), Settings reference.

7. Reading consistently (optional). Turn on select_sequential_consistency when a query must see the latest write, even if it lands on the other replica. It only works together with insert_quorum from item 6: the read waits for, or skips, any replica that does not yet have the latest quorum insert. It makes reads slower, so use it only where needed (for example showing an order right after it was placed) and leave dashboards without it. It can be set in three places, from narrowest to widest:

-- Option 1: on one query only (recommended)
SELECT count() FROM shop.events WHERE shop_id = 42
SETTINGS select_sequential_consistency = 1;

-- Option 2: on the application's connection (every query on it)
SET select_sequential_consistency = 1;
--   in Go: clickhouse.Options{Settings: clickhouse.Settings{"select_sequential_consistency": 1}}

-- Option 3: on the user's profile on the server (every query from that user)
--   file /etc/clickhouse-server/users.d/app.xml on every server; reloaded automatically.
--   A separate reading user, app_reader, gets the setting, so app_writer (item 6) is not affected.
<clickhouse>
  <profiles>
    <app_reader_profile>
      <select_sequential_consistency>1</select_sequential_consistency> <!-- always read the latest quorum write -->
      <readonly>1</readonly>                                            <!-- this user can only read -->
    </app_reader_profile>
  </profiles>

  <users>
    <app_reader>
      <password_sha256_hex from_env="APP_READER_PASSWORD_SHA256"/>
      <profile>app_reader_profile</profile>     <!-- link the user to the settings above -->
      <networks><ip>10.0.0.0/16</ip></networks> <!-- only from inside the VPC -->
    </app_reader>
  </users>
</clickhouse>
