Understanding compression codecs

A codec decides how ClickHouse encodes a column before writing it to disk. The right one can shrink a column from tens of megabytes to kilobytes: less disk, less I/O per query, faster scans. This page explains the codec categories, when to use each, and a test on 10 million rows with the real results.

How codecs work: a chain of steps

Codecs are set per column and can be chained. The usual chain has two steps:

  1. A specialised codec transforms the values so they are easier to compress (for example, turning timestamps into small differences).
  2. A general-purpose compressor then shrinks the resulting bytes.
event_time DateTime64(3) CODEC(Delta, ZSTD(1))
--                             step 1 ^   ^ step 2

Without a CODEC clause a column uses the server default, LZ4. One table can mix codecs freely.

Codec categories

1. General-purpose compressors

They work on any bytes. Use one alone, or as the last step after a specialised codec.

CodecWhat it doesUse case
LZ4 (default)Very fast compression and decompression, moderate ratioHot data queried constantly, where CPU matters more than disk
LZ4HC(level)Slower to write, better ratio, reads as fast as LZ4Data written once and read often
ZSTD(level)Better ratio than LZ4 for a bit more CPU. Levels 1–3 are common; higher for cold dataMost columns, especially strings and anything after a specialised codec
NONENo compressionData that is already compressed or truly random

2. Specialised codecs (value transformations)

They only help when the data has the shape they expect. Always follow them with a general compressor.

CodecWhat it does to the valuesUse case
DeltaStores the difference from the previous value: 10:00:00, 10:00:10, 10:00:20 → 10:00:00, +10, +10Sorted timestamps, increasing IDs, counters
DoubleDeltaStores the change in the difference: +10, +10, +10 → 0, 0, 0Perfectly regular series: metrics sampled every N seconds, monotonic counters
T64Packs each block of integers into only the bits the largest value needs (0–30000 needs 15 bits, not 32)Integers using a small part of their type's range: durations, quantities, status codes
GCDDivides every value by their greatest common divisor: 500, 1500, 2500 → 1, 3, 5Amounts in fixed steps: prices in cents rounded to 5, sizes in 4 KB blocks
GorillaXORs each float with the previous one; slowly changing values leave mostly zero bitsGauges and sensors: temperature, CPU %, price ticks
FPCPredicts the next float from earlier ones and stores only the errorFloating-point data in general, scientific measurements

3. Encoding through data types (not codecs, same goal)

TechniqueUse case
LowCardinality(String)Dictionary encoding for columns with fewer than ~10k distinct values: country, event type, device
Smaller types (UInt16 instead of UInt32, DateTime instead of DateTime64)Values that fit. Halving the type halves the raw size before any codec runs
Enum8 / Enum16A fixed, known set of string values

4. Encryption codecs

AES_128_GCM_SIV and AES_256_GCM_SIV encrypt a column at rest, with keys set in the server config. Use them for sensitive columns such as emails or personal data. Put compression before encryption in the chain, because encrypted bytes don't compress.

The test: each codec on the data it is built for

Run on ClickHouse 25.8 (the single node from Lesson 01), 10 million rows. Each specialised codec is compared with the default LZ4 on exactly the same values:

  • Timestamps: one reading every 10 seconds, perfectly regular.
  • Temperature: a slow sine wave plus random jitter on every reading (Float64).
  • Durations: random 0–30000 stored in UInt32.
  • Prices in cents: random, but always a multiple of 500, stored in UInt64.

The SQL

-- Lesson 02 / extra: each specialised codec on 10M rows of data it is designed for.
-- Run: ch --queries-file /lessons/02-schema-design/05_specialised_codecs.sql
DROP TABLE IF EXISTS default.codec_demo;
CREATE TABLE default.codec_demo (
  ts_lz4        DateTime64(3) CODEC(LZ4),
  ts_delta      DateTime64(3) CODEC(Delta, ZSTD(1)),
  ts_dd         DateTime64(3) CODEC(DoubleDelta, ZSTD(1)),
  temp_lz4      Float64 CODEC(LZ4),
  temp_gorilla  Float64 CODEC(Gorilla, ZSTD(1)),
  temp_fpc      Float64 CODEC(FPC, ZSTD(1)),
  dur_lz4       UInt32 CODEC(LZ4),
  dur_t64       UInt32 CODEC(T64, ZSTD(1)),
  cents_lz4     UInt64 CODEC(LZ4),
  cents_gcd     UInt64 CODEC(GCD, ZSTD(1)),
  cents_zstd    UInt64 CODEC(ZSTD(1))
) ENGINE = MergeTree ORDER BY tuple();
INSERT INTO default.codec_demo SELECT
  toDateTime64('2026-07-01 00:00:00',3) + toIntervalMillisecond(number*10000) AS t,
  t, t,
  20 + 5*sin(number/5000) + (cityHash64(number)%10)/100 AS temp, temp, temp,
  toUInt32(cityHash64(number,1)%30000) AS d, d,
  (cityHash64(number,2)%10000)*500 AS c, c, c
FROM numbers(10000000);
OPTIMIZE TABLE default.codec_demo FINAL;
SELECT name, compression_codec AS codec, formatReadableSize(data_uncompressed_bytes) AS raw, formatReadableSize(data_compressed_bytes) AS on_disk, round(data_uncompressed_bytes/data_compressed_bytes,1) AS ratio
FROM system.columns WHERE table='codec_demo' AND database='default' FORMAT PrettyCompactMonoBlock;

Run it with clickhouse-client --password learn --queries-file 05_specialised_codecs.sql (the same SQL is in lessons/02-schema-design/). OPTIMIZE … FINAL merges all parts first so the sizes are stable.

What the results show

  • Timestamps are the big win. Delta turns a regular series into the same small number repeated, which ZSTD reduces to almost nothing: 49 MiB to 94 KiB. DoubleDelta matches it here and pulls ahead when gaps vary slightly but steadily.
  • T64 halved the durations by storing 15 bits per value instead of 32. Changing the type to UInt16 has a similar effect.
  • GCD beat plain ZSTD on prices (17.9 vs 29 MiB) because every value shrank by a factor of 500 first.
  • Gorilla and FPC gained little because the test added random jitter to every temperature reading. Random noise defeats every codec; smooth real sensor data gains much more.

How to choose a codec

Column looks like…Start with
Timestamps or increasing numbersCODEC(Delta, ZSTD(1)), or DoubleDelta for regular intervals
Small-range integersThe smallest fitting type, or CODEC(T64, ZSTD(1))
Integers in fixed stepsCODEC(GCD, ZSTD(1))
Slowly changing floatsCODEC(Gorilla, ZSTD(1)) or FPC
Repeated strings, few distinct valuesLowCardinality(String)
Free text, URLs, JSONCODEC(ZSTD(3))
UUIDs, hashes, random IDsLeave the default: nothing compresses them

Changing a codec on an existing table

ALTER TABLE shop.events MODIFY COLUMN event_time DateTime64(3) CODEC(Delta, ZSTD(1));
-- New parts use the new codec; existing parts are rewritten as they merge.
-- To rewrite everything now (heavy on big tables):
OPTIMIZE TABLE shop.events FINAL;

Measure before and after

SELECT name, compression_codec,
       formatReadableSize(data_compressed_bytes) AS on_disk,
       round(data_uncompressed_bytes / data_compressed_bytes, 1) AS ratio
FROM system.columns
WHERE database = 'shop' AND table = 'events'
ORDER BY data_compressed_bytes DESC;

Always test on your own data. The shape of the real values decides which codec wins, as the temperature result shows.
