ClickHouse operation and maintenance guide

Procedures for running a self-managed ClickHouse server or cluster day to day: keeping disks from filling up, changing settings on a live system safely, and recovering when something goes wrong. Each section is a self-contained procedure with the background you need, the commands to run, and how to check the result. Where a section uses the tutorial's prod cluster (2 shards × 2 replicas), the commands are given for it as well.

1. System log retention (TTL)

How to put a retention limit on system log tables such as system.query_log, and end up with one table per log instead of a frozen query_log_0 copy next to it. The procedure in 1.4 covers three situations: a new server, an existing table that has not been renamed yet, and a server where the rename already happened.

Verified result. For an existing table, a matching config does not trigger the rename. I read the server source and tested it on ClickHouse 25.8.1.5101 (the version the tutorial cluster runs): after the ALTER and a restart with the matching config, there was still exactly one query_log table, holding its old data and the new TTL. Two conditions apply: the config file must be in place before any restart, and the TTL in the config must be the same expression as the one in the ALTER.

1.1 Why this is needed

On a self-managed server the system log tables (query_log, part_log, trace_log, metric_log and the rest) have no TTL by default. They grow until someone deletes data, which is a common cause of full disks. ClickHouse Cloud is different and keeps them for about 30 days.

The usual fix is a TTL in the server config, for example in config.d/system-logs.xml:

<clickhouse>
  <query_log><ttl>event_date + INTERVAL 30 DAY DELETE</ttl></query_log>
  <part_log><ttl>event_date + INTERVAL 14 DAY DELETE</ttl></part_log>
  <trace_log><ttl>event_date + INTERVAL 7 DAY DELETE</ttl></trace_log>
</clickhouse>

That works cleanly on a new server, because the table is created with the TTL from the start. On a server whose table already exists, it has a side effect that the next section explains.

1.2 Why a config change renames the table

Every system log builds the CREATE TABLE statement it wants from the config: the default engine, partition key and sort key, plus any <ttl>, <partition_by>, <order_by> or <settings> you set. Before it writes, it compares that statement with the definition of the table on disk. If the two differ in any way, it does not alter the table. It renames the table to query_log_0 (then _1, _2 and so on), creates a new empty one from the config, and logs:

Existing table system.query_log for system log has obsolete or different structure. Renaming it to query_log_0.

The rename copies nothing: the old table keeps its files, so a 100 GB query_log becomes a 100 GB query_log_0 that is never written again. The config TTL applies only to the new table. The space comes back only when you drop the old one.

Two details from the source decide how to avoid this:

  • The comparison is on text. Both definitions are formatted to a single line and compared as strings, with the table's UUID removed. In current versions the table comment is ignored as well. So a table that was changed with ALTER passes the check as long as its formatted definition comes out identical to the one built from the config.
  • When it checks. The server reads the table's definition the first time each log flushes after the server starts (and again right after it creates a new table). It keeps that copy for the rest of the process. An ALTER made after that first flush is not compared until the next restart. An ALTER made before it, in the first seconds after startup, is compared at once against the config the server loaded.

The system log section of the config is read only at startup, so editing the file does nothing until a restart.

1.4 Procedure

There are three ways to end up with one system log table that has a TTL. Which one you use depends on the state of the server. Start with the check in 1.4.1, then follow the route that matches what you find.

What you findRouteResult
A new server, or one that has never started1.4.2 Config before the first startTable created with the TTL. Nothing to migrate.
An existing query_log without TTL, and no query_log_01.4.3 ALTER the live table plus matching configSame table keeps its name and data, old rows are deleted in place.
query_log_0 (or _1, _2) already exists1.4.4 Merge the renamed table backMonths you keep are moved back, the old table is dropped.

1.4.1 Check what you have

Note the current TTL (usually none), whether a renamed copy exists, and how much space each month uses:

SELECT name, engine_full
FROM system.tables
WHERE database = 'system' AND name LIKE 'query_log%';

SELECT table, partition, formatReadableSize(sum(bytes_on_disk)) AS size
FROM system.parts
WHERE database = 'system' AND table LIKE 'query_log%' AND active
GROUP BY table, partition ORDER BY table, partition;

Every route uses the same config file. Set only <ttl> in it: other keys such as <partition_by> or <settings> change the table definition as well. Put it in /etc/clickhouse-server/config.d/system-logs.xml on every node:

<clickhouse>
  <query_log>
    <ttl>event_date + INTERVAL 30 DAY DELETE</ttl>
  </query_log>
</clickhouse>

The server reads this section only at startup, so the file does nothing until the next restart.

1.4.2 Route A: config before the first start (new servers)

This is the cleanest route. The table is created from the config with the TTL already in its definition, so the definition never changes and no rename can happen.

  1. Add the config file from 1.4.1 to the server's config.d/ (or your image or configuration management) before the server starts for the first time.

  2. Start the server and check. After SYSTEM FLUSH LOGS, query_log should show TTL event_date + toIntervalDay(30) in engine_full, and there should be no query_log_0. This holds across later restarts as long as the file stays the same.

"First start" means an empty data directory. A server whose data directory already holds the table is an existing server, even if the container or VM is new: use route B.

1.4.3 Route B: ALTER the live table plus matching config (existing table, no rename yet)

Change the TTL on the live table and put the same TTL in the config, so the definitions match at the next restart. The order matters: put the config in place first, so that no restart, planned or not, can happen while the table and the config disagree.

First

Add the config file

Write the TTL into config.d/. Do not restart yet.

Then

ALTER the live table

Same TTL expression, on every node. Old data is deleted in place.

Last

Restart and check

One node first. Confirm there is no query_log_0, then the rest.

  1. Add the config file from 1.4.1 on every node, without restarting.

  2. Optional, for a large table: drop the oldest months first. query_log is partitioned by month by default, so whole months that are already past the window can go instantly instead of being processed by the TTL:

    ALTER TABLE system.query_log DROP PARTITION '202607';
ALTER TABLE system.query_log DROP PARTITION '202608';

  3. Add the TTL to the live table, with the same expression as the config. Do this on a server that has been running for a while rather than seconds after a restart (see section 1.2):

    ALTER TABLE system.query_log MODIFY TTL event_date + INTERVAL 30 DAY;

    By default (materialize_ttl_after_modify = 1) this starts a background MATERIALIZE TTL mutation that applies the TTL to the existing parts and removes expired rows. You can watch it with:

    SELECT command, is_done, parts_to_do
FROM system.mutations
WHERE database = 'system' AND table = 'query_log';

    System tables are local to each server, so run the ALTER on every node.

  4. Restart one node and check it. Then confirm that the table kept its name, its data and the TTL:

    SYSTEM FLUSH LOGS;
SELECT name, engine_full
FROM system.tables
WHERE database = 'system' AND name LIKE 'query_log%';

    You should see one row, query_log, with TTL event_date + toIntervalDay(30) in engine_full. If you see query_log_0, the definitions did not match: compare the Old: and New: lines that follow the "Renaming it to" message in the server log (it is logged at debug level), fix the config, and clean up with route C before restarting the other nodes.

  5. Restart the remaining nodes one at a time and run the same check on each.

Do not run the ALTER without the config. In testing, an ALTER with no matching config was undone at the next restart: the server renamed the altered table to query_log_0 and created a new one without a TTL. The same happens if the ALTER runs in the first seconds after startup, before the first flush.

1.4.4 Route C: merge the renamed table back (server already renamed)

Here a config change already happened: query_log is the new table with the TTL, and the old data sits frozen in query_log_0. Nothing is lost. Move the months you want to keep into the new table, then drop the old one.

  1. Make sure the config file is in place and the server has restarted with it, so the new query_log already has the TTL (check with the first query in 1.4.1).

  2. List the months in the old table and decide which are still inside the retention window:

    SELECT partition, sum(rows) AS rows, formatReadableSize(sum(bytes_on_disk)) AS size
FROM system.parts
WHERE database = 'system' AND table = 'query_log_0' AND active
GROUP BY partition ORDER BY partition;

  3. Attach the months you keep into the new table:

    ALTER TABLE system.query_log ATTACH PARTITION '202609' FROM system.query_log_0;
ALTER TABLE system.query_log ATTACH PARTITION '202610' FROM system.query_log_0;

    ATTACH PARTITION FROM uses hard links, so it is instant and takes no extra disk. It leaves the source table as it was, so the rows are briefly in both tables until the next step. The TTL on the new table then removes any attached rows that are older than the window.

  4. Drop the old table to get the disk space back:

    DROP TABLE system.query_log_0;

    If you want to keep nothing, skip step 3 and only do this. To free space gradually instead, drop it a month at a time with ALTER TABLE system.query_log_0 DROP PARTITION '202609'.

  5. Repeat for every renamed copy (query_log_1, query_log_2 and so on) and on every node, since system tables are local to each server.

ATTACH PARTITION FROM needs both tables to have the same columns, partition key and sort key, and refuses otherwise. That can happen when the rename was caused by a ClickHouse upgrade that changed the columns. In that case copy the rows you want instead, naming the columns the two tables share:

INSERT INTO system.query_log (event_date, event_time, query_id, query, ...)
SELECT event_date, event_time, query_id, query, ...
FROM system.query_log_0
WHERE event_date >= today() - 30;

Unlike ATTACH, this copies the data, so it needs free disk space for the rows you keep until the old table is dropped.

All three routes work for the other logs too. Use the table's own name in both places, for example <part_log> with ALTER TABLE system.part_log. Check each table's TTL column first, since most logs use event_date but not all of them do.

1.5 What counts as matching

Both sides are parsed and then formatted, so spelling differences that format the same way are fine. Anything that formats differently counts as a different table.

Config <ttl>ALTER … MODIFY TTLMatch?
event_date + INTERVAL 30 DAY DELETEevent_date + INTERVAL 30 DAYYes (tested)
event_date + INTERVAL 30 DAYevent_date + toIntervalDay(30)Yes, both format as toIntervalDay(30)
event_date + INTERVAL 1 MONTH DELETEevent_date + INTERVAL 30 DAYNo (tested)
event_date + INTERVAL 30 DAYevent_time + INTERVAL 30 DAYNo, a different column

A ClickHouse upgrade can also change a log's default columns or engine. That still renames the table, whatever TTL you set, and the procedure here does not prevent it.

1.6 On the tutorial cluster

The cluster in cluster/docker-compose.yml mounts each config file into the containers one by one, so a new file needs its own mount line under every ClickHouse service (ch-s1r1, ch-s1r2, ch-s2r1, ch-s2r2):

      - ./clickhouse/config.d/system-logs.xml:/etc/clickhouse-server/config.d/system-logs.xml:ro

A new mount takes effect only when the container is recreated, and recreating it is the restart.

Route A: add the file and the mount lines before the first docker compose up, or after docker compose down -v, which deletes the volumes and all data in them.

Route B: in step 1 you write the file and edit the compose file, but you do not run docker compose up yet. The ALTER from step 3, on each node:

for n in ch-s1r1 ch-s1r2 ch-s2r1 ch-s2r2; do
  docker compose exec -T $n clickhouse-client --password learn \
    -q "ALTER TABLE system.query_log MODIFY TTL event_date + INTERVAL 30 DAY"
done

Then steps 4 and 5, one node at a time:

docker compose up -d ch-s1r1
docker compose exec ch-s1r1 clickhouse-client --password learn -q "SYSTEM FLUSH LOGS"
docker compose exec ch-s1r1 clickhouse-client --password learn \
  -q "SELECT name, engine_full FROM system.tables WHERE database = 'system' AND name LIKE 'query_log%'"

Data lives in the named volumes, so recreating a container keeps the table. To check all four nodes at once:

SELECT hostName() AS host, name, engine_full
FROM clusterAllReplicas('prod', system.tables)
WHERE database = 'system' AND name LIKE 'query_log%'
ORDER BY host, name;

Route C: run the steps on each node, for example docker compose exec ch-s1r1 clickhouse-client --password learn and the same for the other three.
