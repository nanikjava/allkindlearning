POL-AI-003 · authoring to implementation

From Policy to Code

What a policy looks like at each step from the moment someone writes it to the moment it becomes code the gateway runs, and which tools do each step. Every file and output below is real: it comes from the working compiler in ai-standards/redaction-example, where the gateway's tests run against the bundle this pipeline produces.

Stage 1

A user creates the policy

The policy owner fills in a form. The form saves a structured record, not free text, so every rule can later be turned into code without anyone interpreting it.

  • Each statement says how it is enforced: gateway (becomes code), workflow (becomes a step in a release checklist) or attestation (becomes a training or sign-off check).
  • Fields, detectors and actions are dropdowns from closed lists. That is what makes stage 4 safe and automatic.
EditorReact form generated from a JSON Schema (e.g. react-jsonschema-form)
StoragePostgres, one row per version, statements as JSONB
FormatYAML or JSON; YAML shown because it diffs well in review
policies/POL-AI-003.yaml 
policy_id: POL-AI-003
version: "2.1"
title: Data Protection in AI Use
owner: group:privacy-office
approvers: [ciso, dpo]
scope: { apps: all, environments: [prod, staging] }
maps_to: [ISO42001:A.2.2, ISO42001:A.7, OWASP-LLM:LLM02]

statements:
  - id: "3.1"
    text: Personal data must not be sent to externally hosted
      models unless the application is approved for personal data.
    enforced_by: gateway
    applies_when:
      - { field: destination.hosting, equals: external }
    unless:
      - { field: app.approved_for, contains: personal-data }
    detect: [pii.email, pii.phone, pii.national_id]
    action: redact
    on_check_failure: closed

  - id: "3.2"
    text: Payment card numbers and API keys must never be sent to any model.
    enforced_by: gateway
    detect: [pci.card_number, secret.api_key]
    action: block
    on_check_failure: closed

  - id: "3.3"
    text: Customer-facing AI must tell users they are talking to AI.
    enforced_by: workflow
    workflow: release-approval

  - id: "3.4"
    text: Staff who build AI apps complete data protection training yearly.
    enforced_by: attestation
    evidence: lms:ai-data-protection
Stage 2

Relevant people review it

Submitting starts a review workflow. Reviewers are picked from the policy's scope and approver roles. What they look at is generated from the same record:

  • A diff against the current version, in plain language.
  • A preview of the generated code and its tests (stage 4 run in "check only" mode), so engineering can see exactly what will be enforced.
  • A dry run: last week's logged findings replayed through the new rules, showing what would have been blocked or redacted.
WorkflowTemporal (Go SDK): one workflow per version, reviewer actions arrive as signals
Diff / previewThe compiler from stage 4, run without building a bundle
NotifySlack / Teams / email with a link to the review page

Stage 3

The policy is approved

The approvers named in the policy sign. The approval record stores a SHA-256 hash of the exact policy file they approved. This is the link between people and code: the compiler will only build a file whose hash matches a signed approval.

  • The version becomes read-only. Any change is a new version and goes back to stage 1.
  • Authors cannot approve their own policy (separation of duties, enforced from SSO roles).
SigningIn-app e-signature tied to SSO identity (OIDC); optional DocuSign for legal teams that require it
RecordImmutable row in Postgres, copied to the audit store

Stage 4

The policy is implemented as code

Approval triggers a publish job that runs a compiler, policyc. It turns each gateway statement into a rule in Rego, the language of Open Policy Agent (OPA), tests it, and packs it into a signed bundle that gateways download. The OPA engine is embedded in the Go gateway as a library, so evaluating a rule takes under a millisecond and needs no extra service. Whole run, as it prints:

$ go run ./cmd/policyc -policy policies/POL-AI-003.yaml
✓ validated     POL-AI-003 v2.1, 4 statements
✓ approval ok   signed by 2 approvers, content hash matches
✓ generated     2 gateway rules, 8 tests (2 statements enforced outside the gateway)
✓ tests passed  8 of 8
✓ bundle built  build/pol_ai_003-2.1.tar.gz (revision POL-AI-003@2.1+1e9e9d2e, signed)

# and if anyone edits the file after approval:
publish stopped: policy text changed after approval (approved 1e9e9d2e…, now f432eb71…)

  1. Validate

    Checks every field against the closed lists: known detectors, known actions, known input fields, and the right operator for each field (contains for lists, equals for single values). Errors come back to the editor in plain words.

    ToolsGo structs + gopkg.in/yaml.v3; JSON Schema for the editor side
    example rejection 
    policy POL-AI-003 is invalid:
  - statement 3.1: unknown detector "pii.passport"
  - statement 3.1: app.approved_for is a list, use contains

  2. Check the approval

    Loads the approval record, confirms the file's hash matches and that every role in approvers signed. No approval, no code.

    ToolsGo crypto/sha256
    what is compared 
    sha256(policies/POL-AI-003.yaml)  == approval.content_sha256
{ciso, dpo} ⊆ {roles in approval.approvals}

  3. Generate Rego

    Each statement fills a template. Conditions become lines in the rule; unless becomes a not; detectors become the list of finding types. Every value from the policy goes in as a quoted JSON literal, so policy text can never inject code. Statement text becomes a comment so reviewers can match rule to wording.

    ToolsGo text/template
    LanguageRego v1 (OPA's policy language)
    build/src/aiplane/pol_ai_003/policy.rego (generated) 
    # GENERATED by policyc from POL-AI-003 v2.1. Do not edit.
# Source sha256: 1e9e9d2e…25702524
# Approved by: ciso (user:dana), dpo (user:femi)
package aiplane.pol_ai_003

policy_id := "POL-AI-003"
policy_version := "2.1"

default mode := "enforce"
mode := m if m := data.aiplane.rollout[input.app.id][policy_id]

exception_active(statement) if {
	some e in data.aiplane.exceptions
	e.policy_id == policy_id
	e.statement == statement
	e.app == input.app.id
	time.parse_rfc3339_ns(e.expires) > time.now_ns()
}

# Statement 3.1: Personal data must not be sent to externally hosted
# models unless the application is approved for personal data.
decisions contains {"statement": "3.1", "action": "redact",
                    "mode": mode, "finding_ids": ids} if {
	input.destination.hosting == "external"
	not "personal-data" in object.get(input, ["app","approved_for"], [])
	not exception_active("3.1")
	ids := [f.id | some f in input.findings;
	        f.type in ["pii.email","pii.phone","pii.national_id"]]
	count(ids) > 0
}

# Statement 3.2: Payment card numbers and API keys must never be sent to any model.
decisions contains {"statement": "3.2", "action": "block",
                    "mode": mode, "finding_ids": ids} if {
	not exception_active("3.2")
	ids := [f.id | some f in input.findings;
	        f.type in ["pci.card_number","secret.api_key"]]
	count(ids) > 0
}

  4. Generate and run tests

    Tests are generated from the same statements: the rule must fire for each listed data type, stay quiet for other data, and stay quiet when an unless condition holds. If any test fails, publishing stops. Tests are kept out of the bundle.

    ToolsOPA Go SDK tester package (same as opa test)
    one of the 8 generated tests 
    test_s3_1_skipped_when_unless_1 if {
	matched := {d | some d in p.decisions; d.statement == "3.1"}
	  with input as {"app": {"approved_for": ["personal-data"], ...},
	                 "destination": {"hosting": "external", ...},
	                 "findings": [{"id": "f1", "type": "pii.email"}]}
	count(matched) == 0
}

  5. Build a signed bundle

    The rules are packed with the data they read at runtime: exceptions, rollout mode per app (monitor or enforce), and each statement's fail mode. That data comes from the governance database, so a new exception ships without re-approving the policy. The bundle is signed; gateways reject anything that fails verification.

    ToolsOPA Go SDK compile + bundle packages (same as opa build)
    Signing keyDemo uses HS256; production uses RS256/ES256 with the private key in a KMS (AWS KMS, GCP KMS, Vault)
    build/pol_ai_003-2.1.tar.gz 
    /.manifest            {"revision": "POL-AI-003@2.1+1e9e9d2e",
                       "roots": ["aiplane"],
                       "metadata": {"policies": {"POL-AI-003": {
                         "version": "2.1", "content_sha256": "1e9e9d2e…",
                         "maps_to": ["ISO42001:A.2.2", …]}}}}
/.signatures.json     JWT over the hash of every file
/…/policy.rego        the generated rules
/data.json            {"aiplane": {
                         "exceptions": [{"id": "EXC-0042", "app": "claims-assistant",
                                         "statement": "3.1", "expires": "2027-01-31…"}],

                         "policies": {"POL-AI-003": {"statements": {
                           "3.1": {"action": "redact", "on_check_failure": "closed"},
                           "3.2": {"action": "block",  "on_check_failure": "closed"}}}}}}

  6. Distribute and load

    The bundle is uploaded to a bundle server. Each gateway polls it, verifies the signature, compiles the rules once, and swaps them in without a restart. From then on every request through the gateway is evaluated against it.

    Bundle serverS3 / GCS / Azure Blob, or an OCI registry (OPA can pull bundles from both)
    GatewayOPA Go SDK rego + bundle packages, embedded
    policy.go in the gateway 
    vc := bundle.NewVerificationConfig(map[string]*bundle.KeyConfig{
	"policy-signer": {Key: verifyKey, Algorithm: "HS256"},
}, "policy-signer", "", nil)
b, err := bundle.NewReader(f).WithBundleVerificationConfig(vc).Read()
// a bundle signed with any other key fails here

q, err := rego.New(
	rego.Query("data.aiplane.pol_ai_003"),
	rego.ParsedBundle("policies", &b),
).PrepareForEval(ctx)
Statements that are not code

Where workflow and attestation statements go

Only gateway statements become Rego. The same publish job turns the others into configuration for the systems that enforce them.
