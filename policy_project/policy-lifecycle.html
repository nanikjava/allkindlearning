AI Policy Lifecycle

How an AI policy moves from draft to enforced rule and back to review, the situations that start the workflow, and what a policy looks like as a readable document, a structured record, and a rule the gateway runs.

Workflow

The lifecycle

  1. DraftPolicy owner (e.g. privacy office)

    Starts from a template. Writes each statement and marks how it is enforced: by the gateway, by a workflow, or by attestation.

  2. ReviewSecurity, legal, privacy, engineering

    Comments and redlines. Engineering runs a dry run of the rules against last week's traffic to see what would be blocked.

  3. ApproveNamed approvers (CISO, DPO)

    E-sign. The version is frozen and gets an effective date.

  4. PublishSystem

    Statements compile to gateway rules. Rollout can start in monitor-only mode, then switch to enforce.

  5. AcknowledgeEmployees in scope

    Read and accept. Completion is tracked per person as training evidence.

  6. MonitorSystem and owner

    Dashboards show violations, blocks, exceptions and skipped checks per statement.

  7. Review and revisePolicy owner

    Scheduled (e.g. yearly) or triggered by an incident, audit finding or law change. Goes back to Draft as a new version, or is retired.

Every step is logged with who, when and which version, so an auditor can see the full history of any policy.

Use cases

What starts the workflow

SituationWhat happens
First-time setupA new customer picks from a starter pack (acceptable use, data protection, model risk, agent actions, vendor use), adjusts the wording and approves. They are enforcing on day one.
Yearly reviewThe engine opens a review task a month before the date. If nothing changes, the owner re-approves and the evidence shows it was reviewed.
Regulation changesAn EU AI Act or sector rule update is mapped to the affected policies, which reopen with the change highlighted.
IncidentA leak or harmful output is traced to a gap. Corrective action creates a new policy version with a tighter rule.
Audit findingAn auditor notes a statement without evidence. The owner adds an enforcement method or a workflow step.
Exception requestA team needs to break one statement. They get a time-limited exception with compensating controls, attached to that policy version.
New team or app joinsThe app inherits the policies that match its scope (department, risk tier, environment). No manual setup.
RetirementA policy is merged into another or no longer applies. Its rules are removed from the gateway and the record is kept for the audit trail.
Anatomy

One policy, three forms

People write and approve the readable version. The product stores it as a structured record, which is the source of truth. The gateway rule is generated from that record, so nobody hand-writes code to change a policy.

1. What people read and approve

Shown in the product and exported as a PDF for audits
POL-AI-003v2.1Effective 1 Oct 2026Owner: Privacy Office

Data Protection in AI Use

Purpose

Keep personal and sensitive data safe when employees and applications use AI models.

Scope

All AI applications and AI tools used by employees, in production and staging.

Statements

  1. 3.1Personal data must not be sent to externally hosted models unless the application is approved for personal data. gateway
  2. 3.2Payment card numbers, passwords and API keys must never be sent to any model. gateway
  3. 3.3Customer-facing AI must tell users they are talking to AI. workflow
  4. 3.4Staff who build AI applications complete data protection training every year. attestation

Exceptions

Requested through the exception workflow. Maximum six months. Approved by the DPO.

Review

Every 12 months, and after any related incident.

2. What the product stores

Versioned record behind the editor (YAML shown) 
id: POL-AI-003
title: Data Protection in AI Use
version: 2.1
status: published
owner: privacy-office
approved_by: [ciso, dpo]
effective: 2026-10-01
review_every: 12m
scope:
  apps: all
  environments: [prod, staging]
maps_to:                     # reuse evidence across frameworks
  - ISO42001:A.2.2
  - ISO42001:A.7
  - OWASP-LLM:LLM02
  - NIST-AI-RMF:MAP-4.1

statements:
  - id: "3.1"
    enforced_by: gateway
    when: destination.hosting == "external"
    detect: [pii.email, pii.phone, pii.national_id]
    unless: app.approved_for contains "personal-data"
    action: redact
    on_check_failure: closed
  - id: "3.2"
    enforced_by: gateway
    detect: [pci.card_number, secret.password,
             secret.api_key]
    action: block
    on_check_failure: closed
  - id: "3.3"
    enforced_by: workflow
    workflow: release-approval   # checkbox at release
  - id: "3.4"
    enforced_by: attestation
    evidence: lms.course("ai-data-protection")

exceptions:
  - app: claims-assistant
    statement: "3.1"
    expires: 2027-01-31
    approved_by: dpo
    compensating: [self-hosted-model]

3. What the gateway runs

Generated from the record, here as Open Policy Agent (Rego). The gateway's detectors send in their findings; the rule returns a decision. 
package aiplane.pol_ai_003

import rego.v1

blocked_types := {"pci.card_number", "secret.password", "secret.api_key"}
pii_types     := {"pii.email", "pii.phone", "pii.national_id"}

# 3.2  always block card numbers and secrets
decisions contains {"action": "block", "statement": "3.2"} if {
    some f in input.findings
    f.type in blocked_types
}

# 3.1  redact personal data going to external models, unless approved or excepted
decisions contains {"action": "redact", "statement": "3.1", "spans": spans} if {
    input.destination.hosting == "external"
    not "personal-data" in input.app.approved_for
    not exception_active("3.1")
    spans := [f.span | some f in input.findings; f.type in pii_types]
    count(spans) > 0
}

exception_active(sid) if {
    some e in data.exceptions
    e.app == input.app.id
    e.statement == sid
    time.parse_rfc3339_ns(e.expires) > time.now_ns()
}
Design notes

Choices that make this work

  • Every statement has an ID and an enforcement type. Gateway, workflow or attestation. Not everything can be checked by code, and the audit report shows which statements have automatic evidence and which rely on people.
  • Owners use a form editor, not YAML. Detectors, actions and conditions are dropdowns. The YAML and Rego exist for engineers, versioning and export.
  • Monitor mode before enforce. New or changed rules run in log-only mode first, so owners see the impact before anything is blocked.
  • Evidence links to the version. Each gateway decision records the policy ID, version and statement, so a block in March can be traced to the exact wording approved at the time.
  • Store policies like code. Keep the records in a Git-style history with diffs between versions. Customers can also sync them to their own repository.

This is an illustrative example: the policy ID, statements, detector names and control mappings are samples to show the shape, not wording taken from ISO 42001.
